System Design Interview — Master Framework

Six steps. Two goals. One habit you run every time.

Every "design X" prompt — HLD or LLD — collapses into the same repeatable sequence. Steps 1–4 build the skeleton. Step 5 proves it satisfies what the system must do. Step 6 proves it survives what the system must withstand.

1

Requirements

Foundation

What it is

The step where a vague prompt — "design X" — becomes a bounded contract: a short list of things the system must do, and a short list of qualities it must have while doing them.

Why the interviewer cares

This is the highest-leverage step in the interview. Every later decision — entities, API, architecture — gets graded against what you write here. Rush it, and even a technically strong design gets marked down for solving the wrong problem.

The micro-process

  1. Restate the prompt in one sentence, in your own words.
  2. Ask 3–5 clarifying questions that would actually change your design if answered differently — not questions for the sake of asking.
  3. Split findings into two explicit lists: Functional (the verbs — what a user can do) and Non-Functional (the adjectives — scale, latency, availability, consistency, durability, cost).
  4. Rank the functional list and draw a line under the top 3–5. Everything below the line is "acknowledged, out of scope for today."
  5. Say the scope back to the interviewer as a checkpoint before moving on.
Say this out loud

"So to confirm — we're building a system where users can [X], [Y], and [Z]. I'll treat [feature] as out of scope unless we have time at the end. On the non-functional side, I'm assuming roughly [N] users with [latency] reads — does that match what you had in mind?"

Common failure mode

Treating this as a 30-second formality before "the real design" starts. Candidates who skip to boxes-and-arrows almost always end up re-deriving requirements mid-design — which reads as disorganized and burns time you don't get back.

Mini-example — "Design a URL shortener"Functional: (1) shorten a long URL (2) redirect short → long (3) optional custom alias Non-functional: read:write ≈ 100:1 · redirect latency <100ms · codes never collide · links persist indefinitely

Where this shows up differently

  • Infrastructure-style prompts like a rate limiter: the interesting constraints are almost entirely non-functional — latency budget, correctness across instances. The functional list is short enough that debating it for five minutes wastes time you need elsewhere.
  • Consumer-product prompts: functional requirements do the deciding. A small difference like "can a link expire?" ripples all the way through the entity list and API.
  • Pipeline-shaped systems like a web crawler: often need one more non-functional requirement than you'd first guess — something about bounded resource growth (storage, crawl budget) that only becomes obvious once you picture the system running for months, not seconds.
2

Core Entities

Foundation

What it is

Naming the nouns — the handful of objects the whole system is organized around — before touching a schema or class diagram.

Why the interviewer cares

Entities are the shared vocabulary for the rest of the interview. Agree early that this system revolves around "User, Post, Follow relationship" and you can both talk in shorthand for the next 30 minutes instead of re-explaining objects every time.

The micro-process

  1. Reread the functional requirements — every verb usually implies a noun.
  2. List each entity with a 3–5 word description. No attributes yet.
  3. Sketch relationships in one line each (one-to-many, many-to-many) — enough to inform the API step, not a full schema.
  4. Stop there. Attribute-level detail belongs in Data Flow or Deep Dives, not here.
Say this out loud

"Looking at these requirements, I see three core entities: a User, a UrlMapping linking short-code to long-url, and a ClickEvent for analytics. A User has many UrlMappings, and a UrlMapping has many ClickEvents."

Common failure mode

Jumping straight to a full SQL schema with every column and index — premature detail that eats time you need later, and locks in decisions (like SQL vs NoSQL) before you've even designed the API that accesses this data.

Mini-example — URL ShortenerUser (id, plan_tier) UrlMapping (short_code, long_url, owner_id, created_at, expires_at) ClickEvent (url_id, timestamp, referrer)

Where this shows up differently

  • Pipeline-shaped systems like a web crawler: entities often represent the same piece of data at different pipeline stages rather than a fixed set of business objects — a "Frontier entry" and a "Page" both describe a URL, but they're genuinely different entities with different lifecycles. Expect one more entity than you'd first guess, roughly one per meaningful stage.
  • Internal/infrastructure systems like a rate limiter: entities skew toward configuration and live counters rather than anything a user would recognize — "RateLimitRule" and "RequestCounter" aren't nouns from the problem domain, they're nouns from the solution, and that's fine.
  • LLD problems like designing a parking lot: this is where the step goes furthest — entities become real classes with methods, not just fields, and relationships stop being "one line each" and become the actual design (composition, interfaces, inheritance). The class diagram in Step 5 is this step, finished.
3

API / Interface

Foundation

What it is

Turning each functional requirement into a concrete method signature or endpoint — the contract every later component has to honor.

Why the interviewer cares

The API is where "vague feature" becomes "testable interface." It forces decisions on inputs, outputs, and ownership, and gives you a checklist for High-Level Design later: "does my architecture serve every one of these?"

The micro-process

  1. One endpoint or method per functional requirement — no more.
  2. For each: name, inputs, outputs, and the one or two things that can realistically go wrong.
  3. Pick a style — REST, RPC, GraphQL — only if it matters for this system. Say why in one sentence; don't debate it.
  4. Keep it to 3–5 endpoints. More than that usually means Step 1's scope was too wide.
Say this out loud

"For the shorten flow: POST /urls with a long_url and optional custom alias, returns a short_code. For redirect: GET /{short_code} — a 302 to the long URL, or a 404 if it doesn't exist."

Common failure mode

Designing a full CRUD API for every entity "just in case," instead of the specific endpoints the functional requirements actually call for. This bloats the interview and signals template-matching rather than problem-solving.

Mini-example — URL ShortenerPOST /urls {long_url, custom_alias?} → {short_code} GET /{short_code} → 302 redirect | 404 GET /urls/{short_code}/stats → {click_count, created_at}

Where this shows up differently

Not every system centers on a public HTTP API.

  • An internal service like a rate limiter exposes a method signature — allow(client_id) — called by other services, not by end users.
  • A pipeline like a web crawler exposes almost nothing outward at all: an ingestion point to submit seed URLs, and a downstream query interface for whatever consumes the crawled content.

Default to REST out of habit and you'll waste time designing endpoints nobody asked for — say which kind of interface this system actually needs before picking a style.

4

Data Flow

Optional — pipeline systems only

What it is

Tracing how a single piece of data moves, stage by stage, through the system — used only when the core challenge is a pipeline (ingest → transform → store → serve), not a simple request/response system.

Why the interviewer cares

For pipeline-shaped problems (a web crawler, log analytics, video transcoding, feed ranking), the pipeline stages are the architecture — skip this and your High-Level Design becomes boxes with no real sequencing logic. For request/response systems (a URL shortener, a rate limiter), this step usually adds nothing beyond what the API already captured — say so explicitly and move on.

The micro-process

  1. Ask: does data transform across multiple async stages, or is this "request in, response out"? If the latter, skip this step out loud.
  2. If it applies: list the stages in order (e.g. Fetch → Parse → Dedupe → Store → Index).
  3. For each stage, note the trigger (sync call, queue message, schedule) and what it hands to the next stage.
  4. Flag where back-pressure or a stalled stage could block the whole pipeline — this feeds directly into Deep Dives.
Say this out loud

"This is a pipeline problem, so let me trace one page through it: a URL is pulled off the frontier queue, fetched by a worker, parsed for new links and content, deduped against a seen-set, then the content is written to storage and any new URLs go back onto the frontier."

Common failure mode

Either skipping this step for a system where it was the whole point — rushing to a High-Level Design that hides the actual hard part — or forcing it into a simple CRUD system, where it just repeats the API step with extra words.

Mini-example — Web CrawlerFrontier Queue → Fetch Worker → Parser → Dedupe Filter (bloom filter) ↓ ↓ Content Store new URLs → Frontier

Where this shows up differently

The tell for whether this step applies: can you draw the system as a straight line of transformations with no branching decision logic?

  • If yes — a crawler, a log pipeline, a video transcoding job — it's pipeline-shaped, and this step is where the real design happens. See the crawler walkthrough for a fully worked example, including the loop-back that makes a crawler's pipeline different from a simple linear one.
  • If every request is answered by a single synchronous path — a URL shortener, a rate limiter — you're not missing anything by skipping it out loud and moving straight to Step 5.
5

High-Level Design

→ Satisfies Functional Requirements

What it is

The architecture diagram — boxes and arrows from client to storage — walked through once per functional requirement, tracing an actual request through the system rather than presenting a static picture.

Why the interviewer cares

This step proves the system works at all — it's your primary evidence for satisfying Functional Requirements. Interviewers watch whether every box exists because a requirement needs it, not because it's a familiar pattern. You don't need a queue if nothing in your requirements is asynchronous.

The micro-process

  1. Draw components in a consistent order: client → load balancer / gateway → service(s) → cache → database → async workers/queue → CDN — including only what your requirements justify.
  2. Pick your first functional requirement and trace it left to right through the diagram, narrating each hop.
  3. Repeat for each remaining core functional requirement — same diagram, different path through it.
  4. Flag where you're making a default choice ("single relational DB for now, revisit sharding in the deep dive") rather than over-engineering upfront.
Say this out loud

"Let's trace the write path first: a shorten request hits the load balancer, routes to a stateless API service, which generates a code and writes the mapping to the database. Now the read path: a redirect request hits the same service, checks the cache first, falls back to the database on a miss, and issues the 302."

Common failure mode

Presenting the diagram as a finished picture without tracing data through it — "here's my architecture," full stop. This is where the thread connecting design to requirements gets lost, and it's the easiest place for an interviewer to probe and find a gap.

Mini-example — URL Shortener HLDClient → LB → API Service ─┬─ write path → DB ╰─ read path → Cache → (miss) → DB

Where this shows up differently

  • Systems with a write path and a read path that genuinely diverge — like the URL shortener — deserve a diagram that clearly separates them; don't force one static picture to represent both flows if it makes the diagram harder to follow. Trace each path in its own pass through the same boxes, ideally with its own color, the way the worked examples on this page do.
  • Systems built around a single decision point — like the rate limiter — have a simpler HLD but a sharper fork: the diagram's whole job is to make the allow/deny branch and what happens on each side unmistakable.
  • LLD problems replace the service diagram entirely with a class diagram: boxes become classes instead of services, and arrows mean implements/extends and composition instead of network calls. The walkthrough is the same — trace a park and an unpark through the classes — but what you're tracing is method calls in one process, not requests across a network.
6

Deep Dives

→ Satisfies Non-Functional Requirements

What it is

A second, deliberate pass over your Step 5 design — not new diagramming, but taking each Non-Functional Requirement from Step 1 one at a time and asking: does what I built actually survive this, and if not, what changes?

Why the interviewer cares

This is where interviews are actually won or lost. Anyone can draw a load balancer and a cache; showing you know when and why a specific piece breaks under specific conditions — and what you'd change — is the signal that's hard to fake.

The micro-process

  1. List your NFRs from Step 1 again, explicitly.
  2. For each: at the stated scale/latency/availability target, where does the current design break first?
  3. Propose the specific fix — sharding key, cache strategy, replication mode, queue, circuit breaker — and name the trade-off it introduces. Nothing is free.
  4. Go genuinely deep on only 1–2 of these, usually wherever the interviewer leans in. Breadth-first across all NFRs, depth on the one or two that matter most.
Say this out loud

"At 10K redirects/second, a single Postgres instance handling both reads and writes becomes the bottleneck. I'd add read replicas and put a cache in front — since redirects are read-heavy and short codes are immutable once created, cache invalidation isn't even a real concern here, which is a nice property of this specific problem."

Common failure mode

Listing generic scaling techniques — "we'd add a cache, we'd shard the database" — without connecting them to this system's actual numbers or access pattern. This reads as recited vocabulary rather than reasoning, and interviewers can tell the difference immediately.

Mini-exampleNFR "handle 10K redirects/sec" → bottleneck: DB read load → fix: Redis cache keyed by short_code, no TTL needed (mappings are immutable) → trade-off: extra infra + cold-start latency for brand-new links

Where this shows up differently

How many genuine deep dives a system needs varies:

  • A request/response system like the URL shortener usually has one or two (short-code generation, cache design) because there just aren't that many moving parts to stress-test.
  • A pipeline system like the web crawler often has more, because more stages means more places for something to break under scale — duplicate work, politeness, storage growth are all separate failure modes worth their own pass.
  • An algorithm-centric system like the rate limiter can have a deep dive that's almost entirely about a single data-structure choice.
  • An LLD problem like the parking lot swaps scale-shaped deep dives for correctness-shaped ones: race conditions, deadlocks, and whether a design pattern earns its complexity — the non-functional requirements are about a single process behaving correctly under concurrency, not a fleet of servers behaving correctly under load.

Match your depth to what the system actually needs, not to a fixed count you memorized.

Toolkit

Caching Playbook — Search & Hot Keys

Two caching problems that don't fit the simple "cache a key, return a value" shape covered elsewhere on this page: caching something as high-cardinality as free-text search, and protecting a cache from a single key that gets hit far harder than the rest. Both show up directly in the invoice search example below.

Caching free-text search

A simple key-value cache — like the URL shortener's short_code → long_url — has a small, well-defined key space and one stable answer per key. Free-text search breaks both assumptions: the space of possible queries is effectively unbounded, and the correct answer can depend on more than the query string alone.

Cache the query, not (user, query)

Match text once, shared. Filter for permissions after every fetch, hit or miss. Scale-dependent — see the table below.

Normalize before keying

Lowercase, trim, collapse whitespace, so near-identical strings share one entry instead of fragmenting.

Admit by frequency, not by guessing

Only cache a query once it's been seen twice in a short window (Count-Min Sketch). Governs negative results too.

Cache negatives, briefly

A genuine zero-match is a shared negative — short TTL, gated by the same admission policy as everything else.

Debounce on the client

Wait for a pause in typing before sending anything — cuts backend load before it starts.

Two cache tiers

A small local (in-process) cache for the hottest queries per instance, backed by shared Redis for everything else.

Does this hold up at millions of searchers?

Redis's raw throughput usually isn't the bottleneck — a sharded cluster handles millions of ops/sec. The real risk is quieter: a polluted cache doesn't go down, it just stops helping — hit rate collapses and nearly the full query volume gets forwarded to the index anyway, which is what actually falls over while the cache still looks "up." Judge a cache by its hit rate at your actual traffic mix, not by whether it's technically running.

Illustration — admission by frequency, not by guessing"12lasdla" searched once → seen-count: 1 → NOT cached yet "12lasdla" searched again 40 seconds later → seen-count: 2 → NOW admitted to cache "inv-2024-0099" searched once, never again → seen-count: 1 forever → never cached "inv-2024-0088" searched by 6 different people this hour → seen-count: 6 → cached, stays hot The counter itself (a Count-Min Sketch) uses fixed memory no matter how many distinct strings it's seen — so remembering "have I seen this" never becomes its own unbounded cache.
Illustration — why the key design decides whether this scalesPer-(user, query) keys: 5M active users × ~20 distinct searches/user/week ≈ 100M+ keys/week most never requested a second time — memory spent, nothing gained Shared, query-only keys: same week, maybe ~500K genuinely distinct query strings actually searched (many users searching the same or similar invoice numbers, customer names) → roughly 200x smaller key space, and each entry now serves many users, not one

Keeping negative caching honest

"Cache the zero-results too" can quietly become its own burden if it's treated as a separate policy. It isn't one.

SignalWhat to do about it
One-off typos, most negativesThe same frequency-based admission policy from above governs negatives too — a typo nobody repeats never gets written to Redis at all. There's no separate negative-cache policy to maintain or tune.
Negative-cache hit rate is lowDon't reach for a longer TTL — that trades freshness for a hit rate that a longer window usually won't meaningfully fix. If negatives genuinely don't repeat in your traffic, the honest answer is to stop caching them and make sure the index itself resolves "no match" cheaply on its own.
A burst of repeated negative writes (bot, retry loop)That's a rate-limiting problem, not a caching one — bound it at the edge (see the Rate Limiter example), not by tuning cache parameters.

Typos that almost match something real

Prefix matching catches "inv-2024-00" typed partway through — it doesn't catch "vin-2024-0088," a genuine typo of a real invoice number with the wrong letters up front. That needs a different technique, and it comes with a real risk worth naming.

Fuzzy matching is the standard fix

Elasticsearch/OpenSearch's fuzzy query tolerates a small edit distance — insertions, deletions, transpositions — so "vin-2024-0088" can still find "inv-2024-0088."

⚠ IDs aren't names — precision beats recall

Two real invoice numbers are often one digit apart. Silently fuzzy-matching an ID risks returning the wrong document, which is worse than returning nothing.

Fuzzy only as a labeled fallback

Run exact/prefix first. Only on zero results, run a fuzzy lookup and show it as "Did you mean…" — never merged into the primary result list.

Same caching architecture, one more layer

The fuzzy fallback is itself a query — cached by query text, admission-gated by frequency, exactly like everything else above.

Step-by-step — two different users, one cache entry

Two users, subscribed to different products, search the same invoice number nine seconds apart.

  1. User A types "INV-2024-0088." The client waits 300ms after the last keystroke before sending anything.
  2. The query is normalized to "inv-2024-0088" — this is the entire cache key. No user_id in it.
  3. First time anyone has searched this text: cache miss. The Search Service queries the index for the raw match set across all 30+ products and writes it to cache with a 30-second TTL — still unfiltered.
  4. Before returning anything, the Search Service filters that result down to User A's ever-subscribed products and tags each one's status. This step runs regardless of whether the line above was a hit or a miss.
  5. User B searches the identical text nine seconds later: cache hit on the same shared entry — then User B's own subscription filter runs against it, independently. User B may see a different subset of products than User A did, from the exact same cached data.
  6. Net effect: the expensive part (matching text against the index) happened once for both users; the cheap part (who's allowed to see what) ran separately for each of them, every time, with no exceptions.
Strategy by scale

Every card above is a real technique — but applying all of them at 50 QPS is over-engineering, and applying none of them at 5,000 QPS is how a cache quietly stops working. Match the effort to what the traffic actually demands.

~50 QPS
  • Key shape: per-(user, query) — simpler, safer by construction, nothing to get wrong.
  • Skip admission policy and negative-result caching entirely.
  • A plain TTL (30–60s) is enough either way.
100–500 QPS
  • Key shape: per-user is usually still fine — watch actual query diversity, don't assume.
  • Normalize before keying, regardless of shape.
  • Add negative-result caching if typo-heavy traffic is common.
1,000–5,000 QPS
  • Key shape: switch to shared, query-only + filter-after-fetch — the math stops forgiving per-user keys here.
  • Add a cache admission policy and a local (in-process) tier.
  • The filter must never be skipped, on any code path, forever.
5,000+ QPS
  • Everything above is load-bearing, not optional.
  • Shard the cache layer itself (Redis Cluster) if one node's throughput is the limit.
  • Size the index's replica capacity for the residual miss traffic — even 95%+ hit rate still forwards hundreds of QPS.
  • Consider admission control (rate limiting) in front of search entirely.
DecisionThe trade-off
Short TTL vs. long TTLShort keeps results fresh but lowers the hit rate; long improves the hit rate but risks serving stale results — worse here than a simple KV cache, since search results are business data people act on.
Caching negative (zero-result) queriesPrevents repeated typos from hammering the index, at the cost of a small window where a just-indexed record stays invisible until the negative entry's short TTL expires.
Shared query-only cache + filter-after-fetch vs. per-(user, query) cache keysShared keys keep the hit rate real as the user base grows — the permission filter still runs on every single request, cache hit or miss, so nothing is skipped. Per-user keys are simpler to reason about (a cached entry is exactly what was already permitted), but the key space multiplies by active users — at real scale, that's the gap between a cache that works and one that quietly doesn't.
Fuzzy fallback on zero results vs. strict prefix-only matchingCatches genuine typos on structured IDs without risking a silent wrong-document match — fuzzy results are always labeled as suggestions, never merged into exact results — at the cost of an extra, more expensive lookup on every empty search, and a second result type to design and build.

Caching hot keys

A hot key is one cache key that gets far more traffic than the rest — enough that even a well-distributed cluster can have a single node buckling under one key's load, because consistent hashing sends that key to the same place every time. Sharding the cluster doesn't fix this; it only spreads the other keys around it.

Split the key

cache_key:0 through cache_key:N — reads and writes pick a shard at random, spreading one hot key across many nodes.

Local cache for known-hot keys

A small in-process cache in front of the shared one removes the network hop entirely for the traffic that matters most.

Request coalescing

When a hot key expires, one request refetches it while every other concurrent request waits on that result, instead of all of them hitting the store at once.

Refresh before expiry, not after

A background or probabilistic early refresh keeps a genuinely hot key from ever going fully cold — sidestepping the stampede question rather than reacting to it.

Illustration — two ways to relieve one hot keyKey splitting: "trending:productX" (50,000 req/s) → split into 8 shards each request: shard = hash(request_id) % 8 → ~6,250 req/s per shard Local cache vs. shared cache, for a key known to run hot: Redis round trip: ~1–2 ms In-process memory read: ~0.01 ms (100–200x faster)
Step-by-step — a real stampede, prevented

A flash-sale item's price cache expires at the exact moment 200 shoppers are refreshing the page.

  1. The cached price expires at 12:00:00.000.
  2. Without coalescing: all 200 requests miss the cache within the same millisecond and independently query the pricing database — 200x duplicate load arriving at once.
  3. With coalescing: the first request to miss marks the key "in-flight" — a short-lived lock — before fetching the real value.
  4. Requests 2 through 200 see the in-flight marker and wait on that first request's result instead of querying the database themselves.
  5. The first request finishes, writes the price to cache, and clears the marker — all 199 waiting requests read the now-populated cache in the same instant.
  6. Net effect: one database query served 200 requests, instead of 200 queries landing on it simultaneously.
Strategy by scale

Hot-key protection has a cost too — splitting and local caching add real complexity. The question isn't "should I defend against hot keys," it's "at what scale does a hot key become likely enough to justify that cost."

~50 QPS
  • True hot keys are unlikely to matter — full concentration on one key is trivial load for a single node.
  • Plain TTL expiry is fine.
  • Stampede protection here solves a problem that doesn't exist yet.
100–500 QPS
  • Hot keys become theoretically possible.
  • Start with request coalescing — cheap, and covers the one scenario that's now plausible.
  • Splitting and local caching are still premature.
1,000–5,000 QPS
  • A single popular key (a dashboard, a viral query) can now account for a real share of traffic.
  • Add local (in-process) caching + proactive early refresh for keys detected as hot.
  • Key splitting only for genuine outliers — not applied universally.
5,000+ QPS
  • Full toolkit: dynamic hot-key detection, splitting, local caching, coalescing, early refresh.
  • Detection matters — apply this only to keys that are actually hot.
  • Applying it uniformly to every key is its own form of over-engineering.
DecisionThe trade-off
Key splittingSpreads load across nodes, but invalidation and writes now have to reach every shard, not one key — more moving parts for the keys that need it.
Local (in-process) caching for hot keysThe fastest possible read, but reintroduces a small consistency question across every service instance's own cache — usually accepted via a short TTL, not solved outright.
Request coalescingProtects the backing store from a burst of duplicate work, but the one request actually doing the fetch still pays full latency while everyone else queues behind it.

Applying this to Multi-Product Invoice Search

Both playbooks map directly onto decisions already made in that example — worth spelling out explicitly rather than leaving "Cache" as an unlabeled box in a diagram.

Free-text caching → the Cache in front of the Search Index
  • Normalize the query text so equivalent searches collapse into one entry.
  • Cache negative results with a short TTL, so a mistyped invoice number doesn't repeatedly hit the index.
  • Key the cache by the query alone — not (user, query). With 30+ products' worth of users typing typos, a per-user space would explode into millions of entries never requested twice.
  • The subscription filter runs after every fetch — that's what keeps the hit rate real at this scale.
Hot keys → two different places, not one
  • An automated dashboard polling the same query on a schedule is a textbook hot key on the search-result cache — worth coalescing and a short early-refresh.
  • The Subscriptions lookup is actually more likely to go hot — a smaller key space to begin with, one entry per user, not per query.
  • A local cache in front of the shared Subscriptions lookup absorbs a heavy user or shared service account without a network round-trip on every search.

Glossary

The shared vocabulary — reach for these building blocks in Steps 5 and 6, not as buzzwords, but because a specific one solves a specific problem you named.

HLD — Distributed Systems Service architecture & scale

Load Balancer

Distributes incoming requests across multiple servers so no single instance is overwhelmed; enables horizontal scaling and failover.

Reverse Proxy

Sits in front of servers, forwarding client requests to the right backend; often bundles load balancing, TLS termination, and caching.

CDN

A geographically distributed network of edge servers that caches content close to users, cutting latency and origin load.

Cache

A fast, usually in-memory store (Redis, Memcached) holding frequently accessed data to avoid repeated expensive reads.

Cache Invalidation

Keeping cache and source in sync: write-through (both together), write-back (cache first, flush later), write-around (DB only, cache fills on read).

Consistent Hashing

A hashing scheme that minimizes data movement when nodes join or leave, by mapping both keys and nodes onto the same ring.

Sharding / Partitioning

Splitting a dataset across multiple machines by some key, so no single node holds — or serves — all the data.

Leader-Follower Replication

One node accepts writes and propagates them to read-only replicas — trades replication lag for read scalability and durability.

Leaderless Replication

Any node can accept writes, resolved via quorum reads/writes — more availability, more complexity resolving conflicts.

CAP Theorem

Under a network partition, a distributed system must choose between Consistency and Availability — it can't fully have both.

PACELC

Extends CAP: even without a partition, you still trade off Latency against Consistency during normal operation.

ACID

Atomicity, Consistency, Isolation, Durability — the guarantees classic relational transactions provide.

BASE

Basically Available, Soft state, Eventually consistent — the looser guarantee many distributed stores favor for availability and scale.

Message Queue

Holds messages between producers and consumers, decoupling them in time and allowing buffered, async processing.

Pub/Sub

Publishers emit events to a topic; any number of subscribers receive a copy — useful for fan-out.

Idempotency

Performing the same operation multiple times has the same effect as once — critical for safely retrying over unreliable networks.

Rate Limiting

Controls requests per client per window via token bucket (allows bursts), leaky bucket (smooths bursts), or sliding-window counters.

Consensus

Getting nodes to agree on a value or leader despite failures (Raft, Paxos), usually requiring a majority quorum to proceed.

Database Indexing

A secondary structure (often a B-tree) trading extra storage and slower writes for much faster lookups on specific columns.

SQL vs NoSQL

SQL favors strong consistency and relational integrity at some scaling cost; NoSQL favors flexible schemas and horizontal scale, usually looser consistency.

Vertical vs Horizontal Scaling

Vertical adds power to one machine with a hard ceiling; horizontal adds more machines, requiring work to be distributable.

Strong vs Eventual Consistency

Strong guarantees every read reflects the latest write immediately; eventual allows a lag where reads may return stale data.

Circuit Breaker

Stops calling a failing downstream service after repeated errors — failing fast instead of piling up retries and cascading failure.

Backpressure

Lets a slower downstream component signal a faster upstream one to slow down, preventing queues from growing unbounded.

Hot Partition

One shard or key receives disproportionate traffic, becoming a bottleneck even though the system is "sharded."

Fan-out (Push vs Pull)

Push (fan-out-on-write) pre-computes each recipient's feed at write time; pull (fan-out-on-read) computes it at read time — a write-cost vs read-cost trade-off.

Bloom Filter

A space-efficient probabilistic structure answering "definitely not present" or "maybe present" — cheap first-pass dedupe checks.

Replication Factor

The number of copies of each piece of data kept for durability. 3 is the standard default — it survives one node loss while a quorum of 2 remains available.

Little's Law

A queueing identity: average concurrent requests in flight = throughput × average latency (L = λW). Useful for sizing connection pools and thread pools from a QPS and latency estimate.

Availability (The Nines)

Uptime target expressed as a percentage of nines — 99.9% ("three nines") permits about 8.76 hours of downtime a year, 99.99% about 53 minutes. Each extra nine is roughly a 10× tighter budget.

LLD — Object-Oriented Design & Concurrency Class design & single-process correctness

SOLID Principles

Five OOD guidelines: Single Responsibility (one reason to change), Open/Closed (extend without modifying), Liskov Substitution (subtypes must be substitutable), Interface Segregation (many small interfaces beat one fat one), Dependency Inversion (depend on abstractions, not concretions).

Strategy Pattern

Encapsulates an algorithm behind a common interface so it can be swapped at runtime without changing the code that uses it — a pluggable fee calculator or sorting comparator.

Observer Pattern

Objects subscribe to another object and get notified automatically when its state changes — the in-process ancestor of pub/sub.

Factory Pattern

Centralizes object creation behind a method or class, so callers ask for "a spot for this vehicle" instead of knowing every concrete subclass that could satisfy it.

Singleton Pattern

Guarantees a class has exactly one instance with a single global access point. Useful, but a common overuse — it's effectively global mutable state, which complicates testing and concurrency.

Decorator Pattern

Wraps an object to add behavior without modifying its class or affecting other instances — adding logging or caching around a service call.

State Pattern

Encapsulates state-dependent behavior into separate state objects, so behavior changes with internal state without a scatter of if/switch statements.

Composite Pattern

Lets individual objects and groups of objects be treated through the same interface, typically for tree structures — a File and a Folder both responding to getSize().

Interface vs Abstract Class

An interface defines a contract with no implementation; an abstract class can share partial implementation. Favor interfaces when unrelated classes share a capability, abstract classes when they share real code.

Composition over Inheritance

Prefer building behavior by holding references to other objects ("has-a") over deep inheritance chains ("is-a") — composition can change at runtime, inheritance locks in at compile time.

Mutex / Lock

A primitive that lets only one thread hold it at a time, protecting a critical section from concurrent access.

Semaphore

Like a mutex but allows up to N holders at once — caps concurrent access to a limited resource, e.g. a connection pool.

Thread Pool

A fixed set of reusable worker threads pulling from a task queue, avoiding the cost of spawning a new thread per task.

Race Condition

Two or more threads access shared state such that the outcome depends on timing — classic form: check-then-act, where the check and the act aren't atomic.

Deadlock

Two or more threads each hold a resource the other needs and neither can proceed — commonly caused by acquiring multiple locks in inconsistent order.

Producer-Consumer

Producers add work items to a shared queue; consumers pull and process them — decouples creation rate from processing rate, the single-process cousin of a message queue.

Immutability

An object that can't change after construction. Side-steps a large class of concurrency bugs, since there's nothing to race over once an object exists.

Design a URL Shortener

request/response · no pipeline

"Design a service that turns a long URL into a short, shareable one and redirects it back." The cleanest system to run the framework on end-to-end — nothing here distracts from the mechanics.

1

Functional

  • Redirect a short code to its original URL.
  • Optional — per-link click analytics.
  • Optional — links can expire.
Non-functional

  • Codes must never collide.

Key deep dive — short-code generation
FRShorten + custom aliasNFRCodes never collide
Thought process
  1. State the actual requirement: two different long URLs must never end up with the same short code.
  2. First instinct — generate something random. But now every write has to check "has this code been used?" before it can save, an extra round-trip on every single request.
  3. Better instinct: if something already guarantees uniqueness — like an auto-incrementing counter — just encode that into a short string. Collisions become structurally impossible, not just unlikely.
  4. New problem this creates: one shared counter across many servers is a bottleneck. Fix: hand each server its own reserved block of numbers upfront.
  • Counter-based: base62-encode an auto-incrementing ID. Collision-free and simple, but needs a coordinated counter — solved by pre-allocating ID ranges per app server rather than a single global lock.
  • Random-and-check: generate a random string, check the DB for a collision, retry if needed. Trivially distributed, but adds a write-path check on every request.
Illustration — counter-basedid 125,000,000 → base62 encode → "8M0kX"

Either is defensible — the trade-off is what you're paid to articulate. A custom alias skips generation entirely: it's the same uniqueness check as random-and-check, just against a user-supplied string instead of a random one — reject on collision rather than retry with a new one.

Key deep dive — cache design under a 100:1 read:write ratio
FRRedirectFRLinks can expireNFR100:1 read:writeNFR<100ms redirectNFRPersist indefinitely
Thought process
  1. Reads massively outnumber writes, so the cache is doing almost all the real work here — its design deserves real attention, not an afterthought.
  2. Ask the question that shapes everything else: what changes about a mapping after it's created? Nothing — a short_code points to the same long_url forever.
  3. That answer removes a whole category of caching bugs: if nothing changes, there's no "stale data" to invalidate — the only decision left is what to evict when the cache runs out of room.
  4. One thing can still break even a perfect cache: a single link going viral can flood one cache server while the rest of the cluster idles. That's a different problem (a hot key), needing its own fix.

The cache key is simply the short_code, mapping to the long_url — small values, trivially shardable across cache nodes by consistent hashing.

  • No invalidation to design: a UrlMapping never changes after creation, so this is one of the rare caches that just needs an eviction policy (LRU is fine) for memory pressure — no TTL is strictly required.
  • The one real risk — a hot key: a single link going viral can overwhelm one cache node while the rest of the cluster sits idle.
  • If link expiration is in scope, that "no TTL" claim needs qualifying: an expired mapping has to stop resolving, so either the cache entry gets a TTL matching the link's own expiry, or every cache hit checks an expires_at field before returning the redirect. The write-once immutability argument still holds — what changes is "does this row still count," not the row's content.

At that scale, the fix is a short-lived, per-instance local cache in front of the shared cache for the handful of keys receiving disproportionate traffic — so one hot key doesn't become a single point of failure.

Key deep dive — recording clicks without slowing down the redirect
FRClick analytics
Thought process
  1. State the constraint plainly first: the redirect has to be fast, no matter what else the system needs to do.
  2. Ask whether recording the click actually needs to happen before the user gets redirected. It doesn't — the user only cares that they land on the right page instantly, not when the click gets logged.
  3. So don't make the redirect wait on it. Hand the event to a queue and return the redirect immediately — the write happens somewhere else, on its own schedule.
  4. Go one step further: batch the downstream writes instead of one row per click. A few seconds of delay in a dashboard is invisible; writing one row per click at high volume isn't free.

If click analytics are in scope, they cannot sit in the redirect's critical path — every added millisecond there defeats the entire point of a URL shortener.

  • Fire-and-forget: write the click event to a lightweight queue and return the 302 immediately. The redirect never waits for that write to finish.
  • Batch downstream: a consumer drains the queue and writes clicks to the analytics store in batches, trading a few seconds of "when a click shows up in a dashboard" for far lower write amplification than one write per click.

The general habit this reflects: the path that has to be fast and correct (the redirect) never waits on a path that only has to be eventually correct (the analytics). Decouple them with a queue rather than making one request do both jobs.

At 10x scale

Once redirects push past 100K/sec, put a CDN in front of the API for anonymous redirects — the 302 response itself is cacheable at the edge, since a given short_code always redirects to the same long_url. The origin only gets hit on a genuine cache miss anywhere across the entire CDN network, not per-request.

Design a Rate Limiter

internal service · sits in the critical path

"Design a service that limits how many requests a client can make in a given window, usable in front of an API." The interesting decisions here are algorithmic, not architectural.

1
Requirements
Functional
  • Allow/deny a request against a per-client limit (e.g. 100 req/min).
  • Configurable per tier.
  • Return 429 + retry-after when exceeded.
Non-functional
  • Negligible added latency — a few ms at most.
  • Correct across many API server instances simultaneously.
  • Must not take the whole API down if its own storage briefly fails.

Worth asking: is the limit per API key, per user, or per IP? Do different endpoints need different limits? We'll assume per-API-key for this walkthrough.

2

  • Client / API Key — the identity being limited.
  • RateLimitRule (limit, window, scope) — the configured policy, possibly different per tier.
  • RequestCounter (client_id, window_key, count) — the live, fast-changing state checked and incremented on every request.
3
API

Not a public REST API — the interface is a method: allow(client_id) → {allowed: bool, remaining: int, retry_after: seconds}, called by the gateway on every request before it's forwarded anywhere.

4

Skipped — not pipeline-shaped. Every request is a single synchronous check-and-decide, not a multi-stage transformation.

Every request hits the rate limiter's decision point before the backend ever sees it
← scroll to see the full diagram →
Allowed request
  1. Client sends a request to the API Gateway.
  2. Gateway calls allow(client_id) on the Rate Limiter before doing anything else.
  3. Rate Limiter atomically increments the counter for this client's current window in the Counter Store.
  4. Counter is under the limit → Rate Limiter returns allowed: true.
  5. Gateway forwards the request to the Backend Service as normal.

  2. Counter is at or over the limit → Rate Limiter returns allowed: false with a retry_after.
  3. Gateway short-circuits — the Backend Service is never even called.
  4. Client receives 429 Too Many Requests with a Retry-After header.
Key deep dive — algorithm choice
FRAllow / deny a requestNFRNegligible added latency
Thought process
  1. Start with the simplest possible idea: count requests in a fixed time window, reset the count when the window ends. Cheap, easy to reason about.
  2. Stress-test that idea at the boundary: what happens right at the edge of a window? A burst just before reset, plus a burst right after, sails past the limit completely undetected.
  3. Fix the boundary specifically: instead of a hard reset, slide the window continuously — weight the previous window's count instead of discarding it outright.
  4. Consider a different framing entirely: instead of counting within a window, allow a refillable "budget" — useful when some burstiness is actually fine and shouldn't count as a violation.
  • Token bucket: allows controlled bursts, refills smoothly.
  • Leaky bucket: strictly smooths the output rate.
  • Fixed window counter: simplest, but allows up to 2× the limit right at a window boundary.
  • Sliding window counter: more accurate than fixed window, cheaper than a full request log — usually the practical middle ground.
Illustration — the fixed-window boundary problem (limit: 5/min)23:59:59 → 5 requests (window 1) 00:00:01 → 5 more requests (window 2) = 10 requests in 2 seconds, against a "5/min" limit

The counter itself is shared, high-contention state: use an atomic increment (Redis INCR + EXPIRE, or a Lua script) rather than read-then-write, or concurrent requests can race past the limit.

Key deep dive — the counter as a hot key
NFRCorrect across many instances
Thought process
  1. Ask whether sharding actually solves the traffic problem here. It spreads different clients across nodes — but one single client's own counter still lives on exactly one node, no matter how the cluster is sharded.
  2. Locate the real bottleneck: a client hammering the API sends every one of those requests to the same Redis key — concentrated load that sharding can't fix, only spread other clients around it.
  3. Reconsider what "accurate" needs to mean here. A rate limiter doesn't need to be exactly right — only roughly right, and fast to check.
  4. Use that slack: approximate the count locally and flush to Redis periodically, instead of hitting it on every request — trading a little precision for a large drop in load on one key.

A single popular API key can turn its counter into an extremely hot key — thousands of increments per second hitting one Redis key, on one node, regardless of how many nodes the cluster has. Sharding by client_id spreads different clients across nodes but doesn't help a single client's own counter.

Mitigations
  • Approximate the count locally at the gateway with a short flush interval to Redis, instead of hitting Redis on every single request.
  • Accept slightly relaxed accuracy — a rate limiter doesn't need to be exact, it needs to be roughly right and cheap to check.

This is the same class of problem as a viral link in the URL shortener example — a hot key survives sharding, it doesn't get eliminated by it.

Key deep dive — where in the stack to enforce the limit
FRConfigurable per tierNFRNegligible added latencyNFRSurvives storage failure
Thought process
  1. Notice that "where" is a separate decision from "how" — the algorithm and the physical location of the check answer two different questions.
  2. Consider each layer's actual context: the edge sees raw traffic but knows nothing about the user; the gateway sees the full authenticated request; each service knows its own specific cost.
  3. Realize no single layer is strictly correct — each one protects against a different kind of problem, blunt-force abuse versus precise per-operation cost.
  4. Land on the practical answer: layer more than one — cheap and coarse where traffic first arrives, precise and business-aware closer to where the real cost happens.

The algorithm and the storage matter, but so does where the check happens — that decision changes what it can even protect against.

  • At the edge/CDN: cheapest place to block clearly-abusive traffic before it costs you anything downstream, but has the least context — hard to apply per-user business rules there.
  • At the API gateway: the sweet spot for most systems — one place, full request context, before any backend service has done real work.
  • Inside each service: the most precise option — a specific expensive operation can have a tighter limit than a cheap one — at the cost of implementing and maintaining the same logic in every service.

Most real systems layer more than one of these — a coarse, cheap check at the edge, and a precise, business-aware check at the gateway — rather than picking a single layer.

What happens if Counter Store itself is unreachable is a decision worth stating out loud, not leaving implicit: fail open (let requests through) keeps the API up but briefly loses protection; fail closed (reject everything) protects the backend but turns a cache outage into a full outage. Most systems fail open for a rate limiter specifically — a few seconds of unthrottled traffic is a smaller risk than blocking every legitimate request because Redis hiccuped. Per-tier limits are just a lookup ("what's this client's configured limit") that has to be available at whichever layer above ends up enforcing the check — the tier value itself doesn't change where enforcement happens, it's an input to it.

At 10x scale

If Redis round-trips start showing up in tail latency, push the limiter check into the gateway process itself using a local approximate counter (synced to a shared store periodically) rather than a network call on every request. You trade perfect accuracy for near-zero added latency — usually the right trade for a system whose whole job is to shed load, not account for it precisely.

The pipeline loops on itself — every page fetched can discover new URLs that re-enter the Frontier
← scroll to see the full diagram →
One page's trip through the pipeline
  1. A URL is pulled off the Frontier Queue, chosen from a host-partition that isn't currently rate-limited.
  2. A Fetch Worker downloads the page, respecting that host's crawl-delay policy.
  3. The Parser extracts the page's content and every outgoing link it contains.
  4. Each outgoing link passes through the Dedupe Filter: the bloom filter gives a fast "definitely not seen" or "maybe seen" answer; a "maybe" gets checked against the definitive seen-store.

  1. Start with the obvious approach: check every discovered URL against the database of already-crawled URLs before crawling it.
  2. Stress-test that at scale: billions of URLs means billions of lookups — and most of them will say "not seen" anyway, so most of that cost is wasted.
  3. Ask whether the expensive check is even needed for the common case. It isn't — most discovered URLs really are new; the database round-trip only matters for confirming the rare case.
  4. Add a cheap, fast, in-memory pre-check that can instantly say "definitely never seen" for most URLs, and only fall back to the slow, real check when it's genuinely uncertain.

Checking billions of URLs against a full database on every discovered link doesn't scale — a single Bloom filter check is O(1) and lives entirely in memory.

Illustration — the two-stage checknew URL discovered → Bloom filter says "definitely not seen" → crawl it, no DB hit → Bloom filter says "maybe seen" → check the definitive seen-store
  • The filter isn't the source of truth — it's a cheap gate in front of one, catching the vast majority of "definitely new" links without ever touching the database.
  • False positives ("maybe seen" for a URL that's actually new) are rare and fall back to the real check — the trade-off is memory used by the filter versus queries saved, tuned by the filter's false-positive rate.
Key deep dive — politeness at scale
FRPoliteness / robots.txtNFRResilient to host failures
Thought process
  1. State the actual rule that needs enforcing: don't hit any single host too fast, no matter how many crawl workers are running in parallel.
  2. Notice the risk with many independent workers sharing one queue: nothing stops two different workers from pulling URLs for the same host at the same moment.
  3. Reframe the problem: instead of trusting every worker to remember and coordinate pacing, make violating it structurally impossible — organize the work itself by host.
  4. Partition the queue by host, so a worker literally can't fetch from a rate-limited host — its URLs simply aren't eligible to be pulled yet.

Partition the Frontier by host (or a hash of the host). Each partition owns pacing for its set of domains.

  • The mechanism: workers pulling from a partition enforce a per-host delay before the next fetch to that same host — a worker literally cannot fetch from a rate-limited host because that host's URLs simply aren't eligible to be pulled yet.
  • The bonus: this composes naturally with fault tolerance — if one host is slow or down, its partition backs up without affecting any other host's crawl progress.

Politeness becomes a property of the queue's partitioning strategy, not something bolted on afterward.

Key deep dive — crawler traps and infinite URL spaces
NFRNo infinite loops / duplicate work
Thought process
  1. Notice this is a different problem from duplicate crawling above — that's about re-visiting a URL you've genuinely already seen; this is about a site inventing new-looking URLs faster than you can crawl them.
  2. Recognize a dedupe filter can't catch this alone — every one of those URLs genuinely looks different (a new session ID, a different tracking param), so nothing gets flagged as "already seen."
  3. Attack the root cause instead: most of those "different" URLs are actually the same page, decorated with noise. Strip that noise before the dedupe check even runs, so the filter sees one canonical form.
  4. Add a backstop for whatever normalization can't catch: cap how much crawl budget any single host can consume, so one badly-behaved site can't run away with the whole crawl.

Some sites generate an effectively infinite number of distinct URLs — a calendar page with a "next month" link, or a session ID appended to every link — and a naive crawler will happily follow them forever. This is a different failure mode from the duplicate-crawling deep dive above: that one is about re-crawling a URL you've truly already seen; this one is about a site inventing new URLs faster than you can crawl them, which no dedupe filter alone can catch.

Illustration — normalize before dedupe?sid=8f3a&page=2 → normalize → page=2 ?page=2&sid=91cd → normalize → page=2 (recognized as the same page)
  • Normalize URLs before they ever reach the Dedupe Filter — strip session IDs and tracking parameters, sort query params — so the filter sees one canonical form, not endless variations of the same page.
  • Cap crawl depth and URL count per host, so one badly-behaved site can't consume unbounded crawl budget on its own.

A host whose discovered-URL count grows suspiciously fast relative to its actual content is worth flagging for review rather than trusting the crawler to sort it out on its own.

Key deep dive — extensible crawl priority
FRExtensible crawl priorityNFRBounded storage growth
Thought process
  1. Start from the default: every discovered URL gets crawled and re-crawled on the same schedule, no matter what kind of page it is.
  2. Notice that wastes effort — a news homepage changes hourly, a documentation page might not change for years, but a uniform schedule treats them identically.
  3. Ask what would let the crawler spend its budget where it actually matters: a per-page signal for "how often is this worth re-checking," not a global constant.
  4. Attach a priority score to each Frontier entry and let it drive re-crawl frequency — pages that historically change often get shorter intervals, stable pages get longer ones.

Once a single content-hash comparison on re-crawl isn't enough to justify the fetch cost, a priority scoring pass before pages re-enter the Frontier pays off — pages that change often (news, forums) get shorter re-crawl intervals than pages that rarely change (documentation, archives), so crawl budget goes where freshness actually matters instead of being spent uniformly.

  • The signal is behavioral, not declared: track how often a page's content hash actually changes between re-crawls, and let that history — not a manually assigned category — set its priority.
  • This is also what bounds storage growth: a page that rarely changes gets re-fetched rarely, which caps how much duplicate-content churn the Content Store absorbs over time.

Key deep dive — the concurrency race for the last spot
FRPark a vehicleNFRThread-safe, multiple gatesNFRNo full-spot scan
Thought process
  1. Walk through the naive version step by step: check if the spot is free, then mark it occupied — two separate steps.
  2. Ask what happens if two cars run those same two steps at the exact same instant. Both checks can see "free" before either marking happens — nothing stops that.
  3. Realize the bug isn't in either step alone — it's the gap between checking and acting. Two threads can both pass the check before either one acts.
  4. Close the gap: make check-and-mark a single atomic operation, so no other request can slip in between them.

Two cars can approach the last available spot in the same level at the same instant.

Illustration — check-then-act raceCar A: checks spot → "free" Car B: checks spot → "free" (both pass the check) Car A: marks spot occupied Car B: marks spot occupied → two tickets, one physical spot
  • The fix: make spot assignment atomic — either a lock scoped to the level's free-spot list held across the check-and-mark, or a compare-and-swap on the spot's status field if the runtime supports lock-free atomics.
  • The broader principle: any time two threads can both pass a check before either acts on it, you have this same bug — whether it's a parking spot, a bank balance, or the rate limiter's counter from the earlier example.
  • This is also what avoids scanning every spot: "the level's free-spot list" in the fix above isn't incidental phrasing — each Level maintains its own small set of currently-free spots, so assignment is a lookup against that set, not a scan of every spot's status on every request.
Key deep dive — why these specific patterns
FRCompute fee on exitFRMultiple vehicle typesNFRExtensible without rewrites
Thought process
  1. Before reaching for any pattern, ask what's actually likely to change. For fee calculation, that's the pricing scheme — it shifts far more often than the rest of the parking logic.
  2. For spot status, ask a different question: does behavior genuinely differ by state? Yes — an Available spot accepts a car, an Occupied or OutOfService spot rejects one.
  3. Match the tool to the actual shape of the problem: Strategy for "same operation, different implementation" (fee calc), State for "behavior that depends on which state you're in" (spot status).
  4. Apply the real test before committing to either: does it delete a category of future bug, or is it just vocabulary? If it's just vocabulary, a plain conditional is more honest.
  • Strategy for fee calculation: pricing schemes change more often than the core parking logic — a mall might switch from hourly to flat-rate for an event without anyone touching ParkingLot.
  • State for spot status: a spot's behavior genuinely depends on what state it's in — Available accepts a car, Occupied and OutOfService both reject one — so a state object per status keeps that branching out of ParkingSpot itself, rather than the class filling up with scattered status checks.

The test for reaching for a pattern at all: does it delete a category of future bug, or is it just vocabulary? If a pattern doesn't earn its complexity, a plain conditional is more honest code.

Key deep dive — notifying other systems when availability changes
FRReport availability per level
Thought process
  1. List out who actually needs to know when a spot opens: a sign, an app, maybe a pricing service — more than one, and the list is likely to grow.
  2. Reject the naive option first: having every interested system poll the spot's status on its own schedule works, but "who cares about this" ends up hardcoded, scattered across every one of them.
  3. Flip the direction of the relationship: instead of others repeatedly asking "did it change?", have the spot announce "it changed" once, to whoever's listening.
  4. Recognize the win: ParkingLot never needs to know what a "sign" or an "app" even is — it just publishes changes, and each subscriber decides what to do with them.

A real deployment usually has more than one thing that cares when a spot opens up — a digital sign at the entrance, a mobile app showing live availability, maybe a pricing service that raises rates as a lot fills up.

  • The Observer pattern fits directly: ParkingSpot (or Level) maintains a list of observers and notifies them on every state transition, instead of every interested party polling the spot's status on its own schedule.
  • What it decouples: ParkingLot never needs to know what a "sign" or an "app" even is — it just publishes state changes, and whatever's listening decides what to do with them.

This is the in-process ancestor of the pub/sub pattern used at the service level in the crawler and invoice-search examples — same idea, different scale.

Key deep dive — preventing overselling under distributed contention
FRHold a seatFRConfirm purchaseNFRZero overselling
Thought process
  1. Recognize this is the same shape of bug as the parking lot's race — check then act — just spread across many service instances instead of one process.
  2. Notice why a simple lock doesn't scale the same way here: coordinating a distributed lock across many instances adds real overhead, and a new failure mode — what happens if the lock-holder crashes?
  3. Flip the strategy: instead of asking permission before acting, attempt the write and let the database's own atomicity decide who wins — no lock to coordinate, no lock-holder that can crash mid-hold.
  4. Confirm this actually closes the gap: the conditional write only succeeds if the row still matches the expected state, so two simultaneous attempts can't both succeed — one gets 0 rows affected.

Unlike the parking lot's single-process lock, holds here are checked and set across possibly many Booking Service instances hitting the same inventory row at once. A naive "read status, then write Held" is the same check-then-act race from the parking lot, just distributed.

Illustration — the conditional writeUPDATE seats SET status='held' WHERE id = ? AND status = 'available' → succeeds, 1 row affected → this caller wins the seat → 0 rows affected → someone else already holds it

This is optimistic concurrency: don't ask permission first, attempt the write and let the database's atomicity guarantee reject the losers. It scales better than a distributed lock because there's no lock to hold or release — just one conditional write per attempt.

Key deep dive — the virtual waiting room
FRBrowse / see availabilityNFRSurvives a traffic spike
Thought process
  1. Ask where the actual load comes from during a big on-sale — not from people buying seats, but from far more people just looking.
  2. Recognize that's a fundamentally different problem than the seat-hold correctness fix — you can have a perfectly correct hold mechanism and still get crushed by read traffic before anyone even reaches it.
  3. Reframe the goal: don't try to make the backend handle unlimited simultaneous lookers — control how many people are even allowed to reach it at once.
  4. Admit people to the booking flow at a rate the backend can sustain, and give everyone else something better than a broken page — a queue position.

The actual bottleneck in a ticket on-sale usually isn't the seat-holding logic — it's that far more people want to look at seats than could ever buy one, and all that read traffic can crush the same database the holds depend on.

  • What it decouples: "how many people are interested" from "how many people are actively contending for inventory right now," by admitting buyers to the booking flow at a fixed rate the backend can actually sustain.
  • What everyone else sees: a queue position instead of a broken page.

Same shape as the rate limiter's job, aimed at a different goal: the rate limiter protects a service from too much traffic; the waiting room protects fairness and stability during a spike its designers knew was coming.

Key deep dive — bot and scalper prevention
NFRFair-ish ordering under load
Thought process
  1. Ask whether the concurrency fix — the conditional write — actually solves the fairness problem, not just the correctness one. It doesn't: a script can still win hundreds of individually correct writes faster than any human could click.
  2. Recognize this needs a different kind of defense — not "is this write correct," but "is this behavior even human."
  3. Attack it from multiple angles, since no single check reliably distinguishes a fast human from a script: limit how much one account can hold, add friction at entry, and slow down rapid-fire attempts specifically.
  4. Accept that none of these are airtight alone — a determined bot adapts to any single one — so layer several imperfect defenses instead of chasing one perfect check.

Even a perfectly correct hold-and-purchase mechanism doesn't stop a script from acquiring holds on hundreds of seats faster than any human could click — the concurrency fix prevents overselling, not unfair buying.

  • Per-account purchase limits enforced at the same layer as the seat hold — one account can hold at most N seats for a given event at a time.
  • Friction at the waiting-room entry — a CAPTCHA or proof-of-work check adds just enough cost to make large-scale automation expensive, without meaningfully slowing down a real buyer.
  • Rate limiting the hold endpoint itself per account/IP — the same rate-limiter pattern from earlier in this framework, aimed specifically at slowing rapid-fire hold attempts.

None of these are airtight alone — bots adapt to each one — which is why real systems layer several imperfect defenses rather than searching for one perfect one.

Key deep dive — releasing an expired hold
FRRelease hold automatically
Thought process
  1. State the requirement plainly: a hold nobody completes has to eventually stop blocking that seat for everyone else.
  2. Consider a periodic sweep alone: a background job scans for expired holds and releases them. Ask what happens between expiry and the next sweep — the seat still shows as held even though the hold is already dead.
  3. Consider checking at the point of use instead: before trusting a seat's stored status, check whether its hold has already expired.
  4. Notice neither is complete alone — a lazy check only fires when someone looks at that exact seat again; a sweep alone leaves a staleness window. Run both.

A Hold carries its own expires_at — nothing needs to actively cancel it for the reservation to become logically invalid the moment that time passes.

  • Lazy check on access: whenever a seat's status is read or written, check hold_expires_at first — if it's passed, treat the seat as Available regardless of what the stored status literally says, and update the row opportunistically.
  • Periodic sweep: a background job releases expired holds even for seats nobody's actively querying, so aggregate availability (the browse page) doesn't drift stale indefinitely.

The lazy check keeps the path that matters most — someone requesting that exact seat — instantly correct without waiting on a sweep interval; the sweep keeps everything else roughly honest in the meantime. Same "correctness on the hot path, eventual consistency elsewhere" split as the URL shortener's async click recording.

  1. Start from the normal assumption for most web services: any server behind the load balancer can handle any request. Test whether that holds here.

A group message needs the same online/offline delivery decision made independently for every participant, not just one recipient — for a 500-person group, sending is now closer to the fan-out problem than a single message.

Key deep dive — no lost messages, correct order
NFRNo message lossNFRCorrect ordering
Thought process
  1. Ask what "no message loss" actually rules out: a delivery attempt is allowed to fail — a gateway can crash mid-push — but the message itself must never disappear because of that.
  2. Locate the one step that has to be non-negotiable: the message must be durably written before the system does anything else with it, including trying to deliver it.
  3. Once that's true, delivery becomes a retry problem, not a data-loss problem — a failed push just means try again from the durable copy, not "the message is gone."
  4. For ordering, don't assume it's free: two messages sent close together can arrive at the store slightly out of send order, so ordering needs its own explicit key, not just "whichever wrote first."

Both guarantees come from the same discipline: the Message Store is written to first, before any delivery attempt, and every message gets an ordering key that doesn't depend on when a push happened to succeed.

  • Write before you push: a message is durably persisted the moment it's accepted, before the system attempts the WebSocket push or the offline path. A crashed gateway or a failed push is retried against the durable copy — it never means the message itself was lost.
  • Order by a monotonic key, not wall-clock time alone: a per-conversation sequence number (or a timestamp with a tie-breaking id) survives clock skew and near-simultaneous sends; sorting purely by sent_at from different servers can't guarantee that.

Same instinct as Ticketmaster's seat hold and the URL shortener's click recording: identify the one write that has to be correct and durable, and let everything after it — delivery, retries, display — be the part that's allowed to be eventually consistent.

Key deep dive — finding nearby drivers fast

Thought process
  1. Start with the naive approach: for a given rider, check the distance to every driver and pick the closest ones. Test it against scale.

Key deep dive — storing recurring meetings
FRRecurring meetingsFRCancel/modify a single occurrenceNFRNo pre-generating years of instances
Thought process
  1. Consider the simplest option: generate every future occurrence the moment the series is created. Test it against "forever" — a weekly meeting with no end date means either an arbitrary cutoff or unbounded storage.
  2. Consider the opposite extreme: store only the rule, compute occurrences on the fly whenever someone asks. Test it against the common case — now every availability check does that computation, every single time.
  3. Notice neither extreme is right on its own — one wastes storage on meetings nobody will query yet, the other repeats the same computation on every read.
  4. Split the difference deliberately: materialize a bounded near-term window for fast, simple queries, and only compute on demand for anything further out.
  • Materialize on write: generate every instance of the series up front. Simple to query, but wasteful — a weekly meeting "forever" means either an arbitrary cutoff or unbounded storage, and changing the series means rewriting every future instance.
  • Expand on read: store just the rule, compute instances when a range is queried. Cheap to store, but every availability check now does more work, and modifying or canceling a single occurrence needs an "exception" record layered on top of the rule — either "this date is cancelled" or "this date is rescheduled to X" — rather than a row to simply edit or delete.

Most real systems land on a hybrid: materialize a bounded near-term window (say, the next 90 days) for fast queries, and expand on demand beyond that — the same instinct as the crawler's priority scoring, spending effort where it's actually needed.

Write side (30+ independently-owned services) and read side (one shared index) meet only at the event stream — never at query time. Every query is filtered by Subscriptions before results are returned.

Write path (per product, unchanged)
  1. A product's invoice service creates or updates an invoice in its own database, exactly as it always has.
  2. That change emits an event onto the shared Event Stream — the only new thing each product team has to do.
  3. The product's own service never waits on search, never calls it, never knows it exists.
Read path (search)
  1. Client types a free-text query — e.g. a partial invoice number or customer name.
  2. Search Service checks the Cache for this exact query text — the cache key is the query alone, shared across every user, not per-caller.
  3. On a miss, it queries the Search Index for the raw, unfiltered match set across all 30+ products and writes it to cache — still unfiltered, since the text-match itself doesn't depend on who's asking.
  4. Before returning anything, the Search Service filters that result down to the caller's ever-subscribed products (looked up from Subscriptions, cached separately) and tags each one's status. This filter step runs on every request, whether the query above was a cache hit or a miss.
  5. Client groups the results by product before displaying — one aggregated view of only what this user is allowed to see.

Thought process
  1. Start with the most direct-sounding idea: fan a search request out to all 30+ product databases and merge whatever comes back.
  2. Trace what happens to latency: the response can only be as fast as the slowest of 30+ independent calls — with that many in flight, something is always slow.
  3. Trace what happens to ownership: each product team now has to build and maintain search capability on their own schema, for a use case they don't actually own.
  4. Realize the fix isn't "make the fan-out faster" — it's not fanning out at query time at all. Separate the write side (30+ databases, unchanged) from a single purpose-built read copy that every search hits instead.

The naive approach — fan a search request out to all 30+ product databases and merge the results — fails for reasons that compound as the product count grows.

  • Tail latency amplification: the response is only as fast as the slowest of 30+ services on that request — with enough independent calls, something is always slow.
  • Permanent coupling: each product team now has to expose and maintain ad hoc search/filter capability on their own schema, for a use case they don't own.
  • Schema fragmentation: 30+ teams' slightly different ideas of "customer" or "amount" turn a simple query into a fragile integration problem, repeated 30+ times.
  • Grouping gets hard too: merging and grouping 30+ separate, differently-shaped result sets into one "Product A / Product B / …" view is real work, done on every single search.

The fix is CQRS: separate the write model (30+ independently-owned databases) from the read model (one denormalized, purpose-built search index). Reads never touch the write side at query time — and since every product's data already lives in the same index with the same shape, grouping by product is a trivial reshape of one result set, not a live merge of 30+.

Thought process
  1. Given the read side is now a separate copy, ask the obvious follow-up: how does it ever find out about a new or changed invoice?
  2. Reject the direct-call option first: if the Indexer called each product service directly, a slow or down Indexer would now be able to block someone else's invoice write — exactly the coupling CQRS was meant to remove.
  3. Decouple the two sides properly: producers publish what happened, a consumer picks it up on its own schedule — neither side waits on the other.
  4. Choose how the "what happened" gets published: either read it straight from each database's own change log (CDC), or have each service explicitly emit an event — both land on one shared stream either way.

Change Data Capture (CDC) reads each product database's write-ahead log directly, or each product service explicitly publishes an event on every invoice change — either way, changes land on one shared event stream that the Indexer consumes to keep the Search Index current.

  • Same idea as a message queue: producers (30+ product services) and the consumer (the Indexer) never call each other directly, so a slow or down Indexer doesn't block anyone's invoice writes.
  • Schema freedom: a product team can change their own internal schema freely, as long as the event contract stays the same.
  • The Cache pays off here too: a small number of queries (a customer's own recent invoices, a common date-range report) repeat often enough that caching them costs little and saves real load on the index — see the Caching Playbook for the free-text-specific strategy (normalization, negative-result caching) and the hot-key handling this design actually needs.
Key deep dive — enforcing subscriptions on every query
FROnly subscribed products in resultsFRLapsed subscriptions still findableNFRSubscription changes take effect immediately
Thought process
  1. Start with the obvious-seeming fix: bake a product_id IN (…) filter into the search query itself, scoped to whatever the caller is subscribed to.
  2. Trace the side effect of that choice: the query's result now depends on who's asking, not just what they typed — two users searching identical text get different results.
  3. Connect that to the caching work already done: a result that differs per user can't be cached once and shared — the key has to become (user, query), which is exactly the key-space explosion already ruled out.
  4. Move the filter instead of removing it: let the text-match stay caller-blind and shareable, then apply the subscription filter to that (usually small) result afterward, on every single request, cache hit or miss.

Different users subscribe to different subsets of the 30+ products, a subscription change has to take effect immediately, and losing access to a product shouldn't erase the ability to find invoices from when access was active — all while the search cache itself has to stay shared, not per-user, or it collapses under real traffic (see the Caching Playbook).

  • Filter after the fetch, not baked into the query — on purpose: the obvious-seeming alternative is a product_id IN (…) clause baked into the search query itself. That works, but it makes the query's result a function of who's asking, not just what they typed — two users searching identical text get different results, so the cache key has to become (user, query), and that's exactly the key-space explosion the Caching Playbook walks through. Instead, the text-match query never mentions the caller, so it's cacheable once and shared across everyone searching similar text — and the Search Service filters that (usually small) result down to this caller's ever-subscribed products afterward, on every request, cache hit or miss, nothing skipped.
  • Tag status after filtering, not instead of it: for each product that survives the filter, a null unsubscribed_at means "Active"; a set one means "Subscription ended [date]." The tag is a label on an already-permitted result, not a second access check.
  • Cache the subscription history separately, keyed by user: it changes rarely relative to how often a user searches, so this specific lookup — user_id to product list — is cached (Redis, short TTL). This is the one place a user_id belongs in a cache key here; the search-result cache stays query-only and shared, precisely so it doesn't multiply by user count the way this smaller lookup safely can.

This is a deliberate product decision, not a default — "unsubscribe" here means "stop seeing new activity from," not "revoke my own history." A system where that distinction matters for compliance or security should make it explicit, not inherit whichever reading was easiest to build.

Key trade-offs

DecisionThe trade-off
CQRS (separate read/write models) vs. one shared databaseThe read side scales independently with zero coupling to 30+ write schemas, but search results are now eventually consistent — lagging real invoices by seconds — and there are two systems to operate instead of one.
CDC vs. application-level explicit eventsCDC requires no code change from product teams, but needs infrastructure access to each database's write-ahead log; explicit events are simpler to reason about, but every product team must remember to emit them correctly.
One shared search index vs. per-product indices + a federated query layerOne schema and trivial cross-product grouping, at the cost of a bigger blast radius — the whole search experience degrades if that one index has a problem, and a schema change affects every product's data at once.
Query-time subscription filtering vs. index-time ACL taggingQuery-time makes access changes effective immediately with no reindex, at the cost of an extra (cached) lookup on every search; baking permissions into each document at index time avoids that lookup, but a user who just lost access keeps seeing results until the affected documents are reindexed.
Surfacing lapsed subscriptions (tagged) vs. a hard cutoff on unsubscribePreserves a user's ability to reference their own history, at the cost of a broader exposure surface over time — "unsubscribed" no longer means "invisible," which has to be an explicit choice for any system where losing access is meant to fully revoke visibility.
