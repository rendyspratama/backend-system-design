System Design Interview — Master Framework

Six steps. Two goals. One habit you run every time.

Every "design X" prompt — HLD or LLD — collapses into the same repeatable sequence. Steps 1–4 build the skeleton. Step 5 proves it satisfies what the system must do. Step 6 proves it survives what the system must withstand.

1

Requirements

Foundation

What it is

The step where a vague prompt — "design X" — becomes a bounded contract: a short list of things the system must do, and a short list of qualities it must have while doing them.

Why the interviewer cares

This is the highest-leverage step in the interview. Every later decision — entities, API, architecture — gets graded against what you write here. Rush it, and even a technically strong design gets marked down for solving the wrong problem.

The micro-process

  1. Restate the prompt in one sentence, in your own words.
  2. Ask 3–5 clarifying questions that would actually change your design if answered differently — not questions for the sake of asking.
  3. Split findings into two explicit lists: Functional (the verbs — what a user can do) and Non-Functional (the adjectives — scale, latency, availability, consistency, durability, cost).
  4. Rank the functional list and draw a line under the top 3–5. Everything below the line is "acknowledged, out of scope for today."
  5. Say the scope back to the interviewer as a checkpoint before moving on.
Say this out loud

"So to confirm — we're building a system where users can [X], [Y], and [Z]. I'll treat [feature] as out of scope unless we have time at the end. On the non-functional side, I'm assuming roughly [N] users with [latency] reads — does that match what you had in mind?"

Common failure mode

Treating this as a 30-second formality before "the real design" starts. Candidates who skip to boxes-and-arrows almost always end up re-deriving requirements mid-design — which reads as disorganized and burns time you don't get back.

Mini-example — "Design a URL shortener"Functional: (1) shorten a long URL (2) redirect short → long (3) optional custom alias Non-functional: read:write ≈ 100:1 · redirect latency <100ms · codes never collide · links persist indefinitely

Where this shows up differently

  • Infrastructure-style prompts like a rate limiter: the interesting constraints are almost entirely non-functional — latency budget, correctness across instances. The functional list is short enough that debating it for five minutes wastes time you need elsewhere.
  • Consumer-product prompts: functional requirements do the deciding. A small difference like "can a link expire?" ripples all the way through the entity list and API.
  • Pipeline-shaped systems like a web crawler: often need one more non-functional requirement than you'd first guess — something about bounded resource growth (storage, crawl budget) that only becomes obvious once you picture the system running for months, not seconds.
2

Core Entities

Foundation

What it is

Naming the nouns — the handful of objects the whole system is organized around — before touching a schema or class diagram.

Why the interviewer cares

Entities are the shared vocabulary for the rest of the interview. Agree early that this system revolves around "User, Post, Follow relationship" and you can both talk in shorthand for the next 30 minutes instead of re-explaining objects every time.

The micro-process

  1. Reread the functional requirements — every verb usually implies a noun.
  2. List each entity with a 3–5 word description. No attributes yet.
  3. Sketch relationships in one line each (one-to-many, many-to-many) — enough to inform the API step, not a full schema.
  4. Stop there. Attribute-level detail belongs in Data Flow or Deep Dives, not here.
Say this out loud

"Looking at these requirements, I see three core entities: a User, a UrlMapping linking short-code to long-url, and a ClickEvent for analytics. A User has many UrlMappings, and a UrlMapping has many ClickEvents."

Common failure mode

Jumping straight to a full SQL schema with every column and index — premature detail that eats time you need later, and locks in decisions (like SQL vs NoSQL) before you've even designed the API that accesses this data.

Mini-example — URL ShortenerUser (id, plan_tier) UrlMapping (short_code, long_url, owner_id, created_at, expires_at) ClickEvent (url_id, timestamp, referrer)

Where this shows up differently

  • Pipeline-shaped systems like a web crawler: entities often represent the same piece of data at different pipeline stages rather than a fixed set of business objects — a "Frontier entry" and a "Page" both describe a URL, but they're genuinely different entities with different lifecycles. Expect one more entity than you'd first guess, roughly one per meaningful stage.
  • Internal/infrastructure systems like a rate limiter: entities skew toward configuration and live counters rather than anything a user would recognize — "RateLimitRule" and "RequestCounter" aren't nouns from the problem domain, they're nouns from the solution, and that's fine.
  • LLD problems like designing a parking lot: this is where the step goes furthest — entities become real classes with methods, not just fields, and relationships stop being "one line each" and become the actual design (composition, interfaces, inheritance). The class diagram in Step 5 is this step, finished.
3

API / Interface

Foundation

What it is

Turning each functional requirement into a concrete method signature or endpoint — the contract every later component has to honor.

Why the interviewer cares

The API is where "vague feature" becomes "testable interface." It forces decisions on inputs, outputs, and ownership, and gives you a checklist for High-Level Design later: "does my architecture serve every one of these?"

The micro-process

  1. One endpoint or method per functional requirement — no more.
  2. For each: name, inputs, outputs, and the one or two things that can realistically go wrong.
  3. Pick a style — REST, RPC, GraphQL — only if it matters for this system. Say why in one sentence; don't debate it.
  4. Keep it to 3–5 endpoints. More than that usually means Step 1's scope was too wide.
Say this out loud

"For the shorten flow: POST /urls with a long_url and optional custom alias, returns a short_code. For redirect: GET /{short_code} — a 302 to the long URL, or a 404 if it doesn't exist."

Common failure mode

Designing a full CRUD API for every entity "just in case," instead of the specific endpoints the functional requirements actually call for. This bloats the interview and signals template-matching rather than problem-solving.

Mini-example — URL ShortenerPOST /urls {long_url, custom_alias?} → {short_code} GET /{short_code} → 302 redirect | 404 GET /urls/{short_code}/stats → {click_count, created_at}

Where this shows up differently

Not every system centers on a public HTTP API.

  • An internal service like a rate limiter exposes a method signature — allow(client_id) — called by other services, not by end users.
  • A pipeline like a web crawler exposes almost nothing outward at all: an ingestion point to submit seed URLs, and a downstream query interface for whatever consumes the crawled content.

Default to REST out of habit and you'll waste time designing endpoints nobody asked for — say which kind of interface this system actually needs before picking a style.

4

Data Flow

Optional — pipeline systems only

What it is

Tracing how a single piece of data moves, stage by stage, through the system — used only when the core challenge is a pipeline (ingest → transform → store → serve), not a simple request/response system.

Why the interviewer cares

For pipeline-shaped problems (a web crawler, log analytics, video transcoding, feed ranking), the pipeline stages are the architecture — skip this and your High-Level Design becomes boxes with no real sequencing logic. For request/response systems (a URL shortener, a rate limiter), this step usually adds nothing beyond what the API already captured — say so explicitly and move on.

The micro-process

  1. Ask: does data transform across multiple async stages, or is this "request in, response out"? If the latter, skip this step out loud.
  2. If it applies: list the stages in order (e.g. Fetch → Parse → Dedupe → Store → Index).
  3. For each stage, note the trigger (sync call, queue message, schedule) and what it hands to the next stage.
  4. Flag where back-pressure or a stalled stage could block the whole pipeline — this feeds directly into Deep Dives.
Say this out loud

"This is a pipeline problem, so let me trace one page through it: a URL is pulled off the frontier queue, fetched by a worker, parsed for new links and content, deduped against a seen-set, then the content is written to storage and any new URLs go back onto the frontier."

Common failure mode

Either skipping this step for a system where it was the whole point — rushing to a High-Level Design that hides the actual hard part — or forcing it into a simple CRUD system, where it just repeats the API step with extra words.

Mini-example — Web CrawlerFrontier Queue → Fetch Worker → Parser → Dedupe Filter (bloom filter) ↓ ↓ Content Store new URLs → Frontier

Where this shows up differently

The tell for whether this step applies: can you draw the system as a straight line of transformations with no branching decision logic?

  • If yes — a crawler, a log pipeline, a video transcoding job — it's pipeline-shaped, and this step is where the real design happens. See the crawler walkthrough for a fully worked example, including the loop-back that makes a crawler's pipeline different from a simple linear one.
  • If every request is answered by a single synchronous path — a URL shortener, a rate limiter — you're not missing anything by skipping it out loud and moving straight to Step 5.
5

High-Level Design

→ Satisfies Functional Requirements

What it is

The architecture diagram — boxes and arrows from client to storage — walked through once per functional requirement, tracing an actual request through the system rather than presenting a static picture.

Why the interviewer cares

This step proves the system works at all — it's your primary evidence for satisfying Functional Requirements. Interviewers watch whether every box exists because a requirement needs it, not because it's a familiar pattern. You don't need a queue if nothing in your requirements is asynchronous.

The micro-process

  1. Draw components in a consistent order: client → load balancer / gateway → service(s) → cache → database → async workers/queue → CDN — including only what your requirements justify.
  2. Pick your first functional requirement and trace it left to right through the diagram, narrating each hop.
  3. Repeat for each remaining core functional requirement — same diagram, different path through it.
  4. Flag where you're making a default choice ("single relational DB for now, revisit sharding in the deep dive") rather than over-engineering upfront.
Say this out loud

"Let's trace the write path first: a shorten request hits the load balancer, routes to a stateless API service, which generates a code and writes the mapping to the database. Now the read path: a redirect request hits the same service, checks the cache first, falls back to the database on a miss, and issues the 302."

Common failure mode

Presenting the diagram as a finished picture without tracing data through it — "here's my architecture," full stop. This is where the thread connecting design to requirements gets lost, and it's the easiest place for an interviewer to probe and find a gap.

Mini-example — URL Shortener HLDClient → LB → API Service ─┬─ write path → DB ╰─ read path → Cache → (miss) → DB

Where this shows up differently

  • Systems with a write path and a read path that genuinely diverge — like the URL shortener — deserve a diagram that clearly separates them; don't force one static picture to represent both flows if it makes the diagram harder to follow. Trace each path in its own pass through the same boxes, ideally with its own color, the way the worked examples on this page do.
  • Systems built around a single decision point — like the rate limiter — have a simpler HLD but a sharper fork: the diagram's whole job is to make the allow/deny branch and what happens on each side unmistakable.
  • LLD problems replace the service diagram entirely with a class diagram: boxes become classes instead of services, and arrows mean implements/extends and composition instead of network calls. The walkthrough is the same — trace a park and an unpark through the classes — but what you're tracing is method calls in one process, not requests across a network.
6

Deep Dives

→ Satisfies Non-Functional Requirements

What it is

A second, deliberate pass over your Step 5 design — not new diagramming, but taking each Non-Functional Requirement from Step 1 one at a time and asking: does what I built actually survive this, and if not, what changes?

Why the interviewer cares

This is where interviews are actually won or lost. Anyone can draw a load balancer and a cache; showing you know when and why a specific piece breaks under specific conditions — and what you'd change — is the signal that's hard to fake.

The micro-process

  1. List your NFRs from Step 1 again, explicitly.
  2. For each: at the stated scale/latency/availability target, where does the current design break first?
  3. Propose the specific fix — sharding key, cache strategy, replication mode, queue, circuit breaker — and name the trade-off it introduces. Nothing is free.
  4. Go genuinely deep on only 1–2 of these, usually wherever the interviewer leans in. Breadth-first across all NFRs, depth on the one or two that matter most.
Say this out loud

"At 10K redirects/second, a single Postgres instance handling both reads and writes becomes the bottleneck. I'd add read replicas and put a cache in front — since redirects are read-heavy and short codes are immutable once created, cache invalidation isn't even a real concern here, which is a nice property of this specific problem."

Common failure mode

Listing generic scaling techniques — "we'd add a cache, we'd shard the database" — without connecting them to this system's actual numbers or access pattern. This reads as recited vocabulary rather than reasoning, and interviewers can tell the difference immediately.

Mini-exampleNFR "handle 10K redirects/sec" → bottleneck: DB read load → fix: Redis cache keyed by short_code, no TTL needed (mappings are immutable) → trade-off: extra infra + cold-start latency for brand-new links

Where this shows up differently

How many genuine deep dives a system needs varies:

  • A request/response system like the URL shortener usually has one or two (short-code generation, cache design) because there just aren't that many moving parts to stress-test.
  • A pipeline system like the web crawler often has more, because more stages means more places for something to break under scale — duplicate work, politeness, storage growth are all separate failure modes worth their own pass.
  • An algorithm-centric system like the rate limiter can have a deep dive that's almost entirely about a single data-structure choice.
  • An LLD problem like the parking lot swaps scale-shaped deep dives for correctness-shaped ones: race conditions, deadlocks, and whether a design pattern earns its complexity — the non-functional requirements are about a single process behaving correctly under concurrency, not a fleet of servers behaving correctly under load.

Match your depth to what the system actually needs, not to a fixed count you memorized.

Toolkit

Caching Playbook — Search & Hot Keys

Two caching problems that don't fit the simple "cache a key, return a value" shape covered elsewhere on this page: caching something as high-cardinality as free-text search, and protecting a cache from a single key that gets hit far harder than the rest. Both show up directly in the invoice search example below.

Caching free-text search

A simple key-value cache — like the URL shortener's short_code → long_url — has a small, well-defined key space and one stable answer per key. Free-text search breaks both assumptions: the space of possible queries is effectively unbounded, and the correct answer can depend on more than the query string alone.

Cache the query, not (user, query)

Match text once, shared. Filter for permissions after every fetch, hit or miss. Scale-dependent — see the table below.

Normalize before keying

Lowercase, trim, collapse whitespace, so near-identical strings share one entry instead of fragmenting.

Admit by frequency, not by guessing

Only cache a query once it's been seen twice in a short window (Count-Min Sketch). Governs negative results too.

Cache negatives, briefly

A genuine zero-match is a shared negative — short TTL, gated by the same admission policy as everything else.

Debounce on the client

Wait for a pause in typing before sending anything — cuts backend load before it starts.

Two cache tiers

A small local (in-process) cache for the hottest queries per instance, backed by shared Redis for everything else.

Does this hold up at millions of searchers?

Redis's raw throughput usually isn't the bottleneck — a sharded cluster handles millions of ops/sec. The real risk is quieter: a polluted cache doesn't go down, it just stops helping — hit rate collapses and nearly the full query volume gets forwarded to the index anyway, which is what actually falls over while the cache still looks "up." Judge a cache by its hit rate at your actual traffic mix, not by whether it's technically running.

Illustration — admission by frequency, not by guessing"12lasdla" searched once → seen-count: 1 → NOT cached yet "12lasdla" searched again 40 seconds later → seen-count: 2 → NOW admitted to cache "inv-2024-0099" searched once, never again → seen-count: 1 forever → never cached "inv-2024-0088" searched by 6 different people this hour → seen-count: 6 → cached, stays hot The counter itself (a Count-Min Sketch) uses fixed memory no matter how many distinct strings it's seen — so remembering "have I seen this" never becomes its own unbounded cache.
Illustration — why the key design decides whether this scalesPer-(user, query) keys: 5M active users × ~20 distinct searches/user/week ≈ 100M+ keys/week most never requested a second time — memory spent, nothing gained Shared, query-only keys: same week, maybe ~500K genuinely distinct query strings actually searched (many users searching the same or similar invoice numbers, customer names) → roughly 200x smaller key space, and each entry now serves many users, not one

Keeping negative caching honest

"Cache the zero-results too" can quietly become its own burden if it's treated as a separate policy. It isn't one.

SignalWhat to do about it
One-off typos, most negativesThe same frequency-based admission policy from above governs negatives too — a typo nobody repeats never gets written to Redis at all. There's no separate negative-cache policy to maintain or tune.
Negative-cache hit rate is lowDon't reach for a longer TTL — that trades freshness for a hit rate that a longer window usually won't meaningfully fix. If negatives genuinely don't repeat in your traffic, the honest answer is to stop caching them and make sure the index itself resolves "no match" cheaply on its own.
A burst of repeated negative writes (bot, retry loop)That's a rate-limiting problem, not a caching one — bound it at the edge (see the Rate Limiter example), not by tuning cache parameters.

Typos that almost match something real

Prefix matching catches "inv-2024-00" typed partway through — it doesn't catch "vin-2024-0088," a genuine typo of a real invoice number with the wrong letters up front. That needs a different technique, and it comes with a real risk worth naming.

Fuzzy matching is the standard fix

Elasticsearch/OpenSearch's fuzzy query tolerates a small edit distance — insertions, deletions, transpositions — so "vin-2024-0088" can still find "inv-2024-0088."

⚠ IDs aren't names — precision beats recall

Two real invoice numbers are often one digit apart. Silently fuzzy-matching an ID risks returning the wrong document, which is worse than returning nothing.

Fuzzy only as a labeled fallback

Run exact/prefix first. Only on zero results, run a fuzzy lookup and show it as "Did you mean…" — never merged into the primary result list.

Same caching architecture, one more layer

The fuzzy fallback is itself a query — cached by query text, admission-gated by frequency, exactly like everything else above.

Step-by-step — two different users, one cache entry

Two users, subscribed to different products, search the same invoice number nine seconds apart.

  1. User A types "INV-2024-0088." The client waits 300ms after the last keystroke before sending anything.
  2. The query is normalized to "inv-2024-0088" — this is the entire cache key. No user_id in it.
  3. First time anyone has searched this text: cache miss. The Search Service queries the index for the raw match set across all 30+ products and writes it to cache with a 30-second TTL — still unfiltered.
  4. Before returning anything, the Search Service filters that result down to User A's ever-subscribed products and tags each one's status. This step runs regardless of whether the line above was a hit or a miss.
  5. User B searches the identical text nine seconds later: cache hit on the same shared entry — then User B's own subscription filter runs against it, independently. User B may see a different subset of products than User A did, from the exact same cached data.
  6. Net effect: the expensive part (matching text against the index) happened once for both users; the cheap part (who's allowed to see what) ran separately for each of them, every time, with no exceptions.
Strategy by scale

Every card above is a real technique — but applying all of them at 50 QPS is over-engineering, and applying none of them at 5,000 QPS is how a cache quietly stops working. Match the effort to what the traffic actually demands.

~50 QPS
  • Key shape: per-(user, query) — simpler, safer by construction, nothing to get wrong.
  • Skip admission policy and negative-result caching entirely.
  • A plain TTL (30–60s) is enough either way.
100–500 QPS
  • Key shape: per-user is usually still fine — watch actual query diversity, don't assume.
  • Normalize before keying, regardless of shape.
  • Add negative-result caching if typo-heavy traffic is common.
1,000–5,000 QPS
  • Key shape: switch to shared, query-only + filter-after-fetch — the math stops forgiving per-user keys here.
  • Add a cache admission policy and a local (in-process) tier.
  • The filter must never be skipped, on any code path, forever.
5,000+ QPS
  • Everything above is load-bearing, not optional.
  • Shard the cache layer itself (Redis Cluster) if one node's throughput is the limit.
  • Size the index's replica capacity for the residual miss traffic — even 95%+ hit rate still forwards hundreds of QPS.
  • Consider admission control (rate limiting) in front of search entirely.
DecisionThe trade-off
Short TTL vs. long TTLShort keeps results fresh but lowers the hit rate; long improves the hit rate but risks serving stale results — worse here than a simple KV cache, since search results are business data people act on.
Caching negative (zero-result) queriesPrevents repeated typos from hammering the index, at the cost of a small window where a just-indexed record stays invisible until the negative entry's short TTL expires.
Shared query-only cache + filter-after-fetch vs. per-(user, query) cache keysShared keys keep the hit rate real as the user base grows — the permission filter still runs on every single request, cache hit or miss, so nothing is skipped. Per-user keys are simpler to reason about (a cached entry is exactly what was already permitted), but the key space multiplies by active users — at real scale, that's the gap between a cache that works and one that quietly doesn't.
Fuzzy fallback on zero results vs. strict prefix-only matchingCatches genuine typos on structured IDs without risking a silent wrong-document match — fuzzy results are always labeled as suggestions, never merged into exact results — at the cost of an extra, more expensive lookup on every empty search, and a second result type to design and build.

Caching hot keys

A hot key is one cache key that gets far more traffic than the rest — enough that even a well-distributed cluster can have a single node buckling under one key's load, because consistent hashing sends that key to the same place every time. Sharding the cluster doesn't fix this; it only spreads the other keys around it.

Split the key

cache_key:0 through cache_key:N — reads and writes pick a shard at random, spreading one hot key across many nodes.

Local cache for known-hot keys

A small in-process cache in front of the shared one removes the network hop entirely for the traffic that matters most.

Request coalescing

When a hot key expires, one request refetches it while every other concurrent request waits on that result, instead of all of them hitting the store at once.

Refresh before expiry, not after

A background or probabilistic early refresh keeps a genuinely hot key from ever going fully cold — sidestepping the stampede question rather than reacting to it.

Illustration — two ways to relieve one hot keyKey splitting: "trending:productX" (50,000 req/s) → split into 8 shards each request: shard = hash(request_id) % 8 → ~6,250 req/s per shard Local cache vs. shared cache, for a key known to run hot: Redis round trip: ~1–2 ms In-process memory read: ~0.01 ms (100–200x faster)
Step-by-step — a real stampede, prevented

A flash-sale item's price cache expires at the exact moment 200 shoppers are refreshing the page.

  1. The cached price expires at 12:00:00.000.
  2. Without coalescing: all 200 requests miss the cache within the same millisecond and independently query the pricing database — 200x duplicate load arriving at once.
  3. With coalescing: the first request to miss marks the key "in-flight" — a short-lived lock — before fetching the real value.
  4. Requests 2 through 200 see the in-flight marker and wait on that first request's result instead of querying the database themselves.
  5. The first request finishes, writes the price to cache, and clears the marker — all 199 waiting requests read the now-populated cache in the same instant.
  6. Net effect: one database query served 200 requests, instead of 200 queries landing on it simultaneously.
Strategy by scale

Hot-key protection has a cost too — splitting and local caching add real complexity. The question isn't "should I defend against hot keys," it's "at what scale does a hot key become likely enough to justify that cost."

~50 QPS
  • True hot keys are unlikely to matter — full concentration on one key is trivial load for a single node.
  • Plain TTL expiry is fine.
  • Stampede protection here solves a problem that doesn't exist yet.
100–500 QPS
  • Hot keys become theoretically possible.
  • Start with request coalescing — cheap, and covers the one scenario that's now plausible.
  • Splitting and local caching are still premature.
1,000–5,000 QPS
  • A single popular key (a dashboard, a viral query) can now account for a real share of traffic.
  • Add local (in-process) caching + proactive early refresh for keys detected as hot.
  • Key splitting only for genuine outliers — not applied universally.
5,000+ QPS
  • Full toolkit: dynamic hot-key detection, splitting, local caching, coalescing, early refresh.
  • Detection matters — apply this only to keys that are actually hot.
  • Applying it uniformly to every key is its own form of over-engineering.
DecisionThe trade-off
Key splittingSpreads load across nodes, but invalidation and writes now have to reach every shard, not one key — more moving parts for the keys that need it.
Local (in-process) caching for hot keysThe fastest possible read, but reintroduces a small consistency question across every service instance's own cache — usually accepted via a short TTL, not solved outright.
Request coalescingProtects the backing store from a burst of duplicate work, but the one request actually doing the fetch still pays full latency while everyone else queues behind it.

Applying this to Multi-Product Invoice Search

Both playbooks map directly onto decisions already made in that example — worth spelling out explicitly rather than leaving "Cache" as an unlabeled box in a diagram.

Free-text caching → the Cache in front of the Search Index
  • Normalize the query text so equivalent searches collapse into one entry.
  • Cache negative results with a short TTL, so a mistyped invoice number doesn't repeatedly hit the index.
  • Key the cache by the query alone — not (user, query). With 30+ products' worth of users typing typos, a per-user space would explode into millions of entries never requested twice.
  • The subscription filter runs after every fetch — that's what keeps the hit rate real at this scale.
Hot keys → two different places, not one
  • An automated dashboard polling the same query on a schedule is a textbook hot key on the search-result cache — worth coalescing and a short early-refresh.
  • The Subscriptions lookup is actually more likely to go hot — a smaller key space to begin with, one entry per user, not per query.
  • A local cache in front of the shared Subscriptions lookup absorbs a heavy user or shared service account without a network round-trip on every search.

Glossary

The shared vocabulary — reach for these building blocks in Steps 5 and 6, not as buzzwords, but because a specific one solves a specific problem you named.

HLD — Distributed Systems Service architecture & scale

Load Balancer

Distributes incoming requests across multiple servers so no single instance is overwhelmed; enables horizontal scaling and failover.

Reverse Proxy

Sits in front of servers, forwarding client requests to the right backend; often bundles load balancing, TLS termination, and caching.

CDN

A geographically distributed network of edge servers that caches content close to users, cutting latency and origin load.

Cache

A fast, usually in-memory store (Redis, Memcached) holding frequently accessed data to avoid repeated expensive reads.

Cache Invalidation

Keeping cache and source in sync: write-through (both together), write-back (cache first, flush later), write-around (DB only, cache fills on read).

Consistent Hashing

A hashing scheme that minimizes data movement when nodes join or leave, by mapping both keys and nodes onto the same ring.

Sharding / Partitioning

Splitting a dataset across multiple machines by some key, so no single node holds — or serves — all the data.

Leader-Follower Replication

One node accepts writes and propagates them to read-only replicas — trades replication lag for read scalability and durability.

Leaderless Replication

Any node can accept writes, resolved via quorum reads/writes — more availability, more complexity resolving conflicts.

CAP Theorem

Under a network partition, a distributed system must choose between Consistency and Availability — it can't fully have both.

PACELC

Extends CAP: even without a partition, you still trade off Latency against Consistency during normal operation.

ACID

Atomicity, Consistency, Isolation, Durability — the guarantees classic relational transactions provide.

BASE

Basically Available, Soft state, Eventually consistent — the looser guarantee many distributed stores favor for availability and scale.

Message Queue

Holds messages between producers and consumers, decoupling them in time and allowing buffered, async processing.

Pub/Sub

Publishers emit events to a topic; any number of subscribers receive a copy — useful for fan-out.

Idempotency

Performing the same operation multiple times has the same effect as once — critical for safely retrying over unreliable networks.

Rate Limiting

Controls requests per client per window via token bucket (allows bursts), leaky bucket (smooths bursts), or sliding-window counters.

Consensus

Getting nodes to agree on a value or leader despite failures (Raft, Paxos), usually requiring a majority quorum to proceed.

Database Indexing

A secondary structure (often a B-tree) trading extra storage and slower writes for much faster lookups on specific columns.

SQL vs NoSQL

SQL favors strong consistency and relational integrity at some scaling cost; NoSQL favors flexible schemas and horizontal scale, usually looser consistency.

Vertical vs Horizontal Scaling

Vertical adds power to one machine with a hard ceiling; horizontal adds more machines, requiring work to be distributable.

Strong vs Eventual Consistency

Strong guarantees every read reflects the latest write immediately; eventual allows a lag where reads may return stale data.

Circuit Breaker

Stops calling a failing downstream service after repeated errors — failing fast instead of piling up retries and cascading failure.

Backpressure

Lets a slower downstream component signal a faster upstream one to slow down, preventing queues from growing unbounded.

Hot Partition

One shard or key receives disproportionate traffic, becoming a bottleneck even though the system is "sharded."

Fan-out (Push vs Pull)

Push (fan-out-on-write) pre-computes each recipient's feed at write time; pull (fan-out-on-read) computes it at read time — a write-cost vs read-cost trade-off.

Bloom Filter

A space-efficient probabilistic structure answering "definitely not present" or "maybe present" — cheap first-pass dedupe checks.

Replication Factor

The number of copies of each piece of data kept for durability. 3 is the standard default — it survives one node loss while a quorum of 2 remains available.

Little's Law

A queueing identity: average concurrent requests in flight = throughput × average latency (L = λW). Useful for sizing connection pools and thread pools from a QPS and latency estimate.

Availability (The Nines)

Uptime target expressed as a percentage of nines — 99.9% ("three nines") permits about 8.76 hours of downtime a year, 99.99% about 53 minutes. Each extra nine is roughly a 10× tighter budget.

LLD — Object-Oriented Design & Concurrency Class design & single-process correctness

SOLID Principles

Five OOD guidelines: Single Responsibility (one reason to change), Open/Closed (extend without modifying), Liskov Substitution (subtypes must be substitutable), Interface Segregation (many small interfaces beat one fat one), Dependency Inversion (depend on abstractions, not concretions).

Strategy Pattern

Encapsulates an algorithm behind a common interface so it can be swapped at runtime without changing the code that uses it — a pluggable fee calculator or sorting comparator.

Observer Pattern

Objects subscribe to another object and get notified automatically when its state changes — the in-process ancestor of pub/sub.

Factory Pattern

Centralizes object creation behind a method or class, so callers ask for "a spot for this vehicle" instead of knowing every concrete subclass that could satisfy it.

Singleton Pattern

Guarantees a class has exactly one instance with a single global access point. Useful, but a common overuse — it's effectively global mutable state, which complicates testing and concurrency.

Decorator Pattern

Wraps an object to add behavior without modifying its class or affecting other instances — adding logging or caching around a service call.

State Pattern

Encapsulates state-dependent behavior into separate state objects, so behavior changes with internal state without a scatter of if/switch statements.

Composite Pattern

Lets individual objects and groups of objects be treated through the same interface, typically for tree structures — a File and a Folder both responding to getSize().

Interface vs Abstract Class

An interface defines a contract with no implementation; an abstract class can share partial implementation. Favor interfaces when unrelated classes share a capability, abstract classes when they share real code.

Composition over Inheritance

Prefer building behavior by holding references to other objects ("has-a") over deep inheritance chains ("is-a") — composition can change at runtime, inheritance locks in at compile time.

Mutex / Lock

A primitive that lets only one thread hold it at a time, protecting a critical section from concurrent access.

Semaphore

Like a mutex but allows up to N holders at once — caps concurrent access to a limited resource, e.g. a connection pool.

Thread Pool

A fixed set of reusable worker threads pulling from a task queue, avoiding the cost of spawning a new thread per task.

Race Condition

Two or more threads access shared state such that the outcome depends on timing — classic form: check-then-act, where the check and the act aren't atomic.

Deadlock

Two or more threads each hold a resource the other needs and neither can proceed — commonly caused by acquiring multiple locks in inconsistent order.

Producer-Consumer

Producers add work items to a shared queue; consumers pull and process them — decouples creation rate from processing rate, the single-process cousin of a message queue.

Immutability

An object that can't change after construction. Side-steps a large class of concurrency bugs, since there's nothing to race over once an object exists.

Design a URL Shortener

"Design a service that turns a long URL into a short, shareable one and redirects it back." The cleanest system to run the framework on end-to-end — nothing here distracts from the mechanics.

1

Functional

  • Redirect a short code to its original URL.
  • Optional — per-link click analytics.
  • Optional — links can expire.
Non-functional

  • Codes must never collide.

Key deep dive — short-code generation
FRShorten + custom aliasNFRCodes never collide
Thought process
  1. State the actual requirement: two different long URLs must never end up with the same short code.
  2. First instinct — generate something random. But now every write has to check "has this code been used?" before it can save, an extra round-trip on every single request.
  3. Better instinct: if something already guarantees uniqueness — like an auto-incrementing counter — just encode that into a short string. Collisions become structurally impossible, not just unlikely.
  4. New problem this creates: one shared counter across many servers is a bottleneck. Fix: hand each server its own reserved block of numbers upfront.
  • Counter-based: base62-encode an auto-incrementing ID. Collision-free and simple, but needs a coordinated counter — solved by pre-allocating ID ranges per app server rather than a single global lock.
  • Random-and-check: generate a random string, check the DB for a collision, retry if needed. Trivially distributed, but adds a write-path check on every request.
Illustration — counter-basedid 125,000,000 → base62 encode → "8M0kX"

Either is defensible — the trade-off is what you're paid to articulate. A custom alias skips generation entirely: it's the same uniqueness check as random-and-check, just against a user-supplied string instead of a random one — reject on collision rather than retry with a new one.

Key deep dive — cache design under a 100:1 read:write ratio
FRRedirectFRLinks can expireNFR100:1 read:writeNFR<100ms redirectNFRPersist indefinitely
Thought process
  1. Reads massively outnumber writes, so the cache is doing almost all the real work here — its design deserves real attention, not an afterthought.
  2. Ask the question that shapes everything else: what changes about a mapping after it's created? Nothing — a short_code points to the same long_url forever.
  3. That answer removes a whole category of caching bugs: if nothing changes, there's no "stale data" to invalidate — the only decision left is what to evict when the cache runs out of room.
  4. One thing can still break even a perfect cache: a single link going viral can flood one cache server while the rest of the cluster idles. That's a different problem (a hot key), needing its own fix.

The cache key is simply the short_code, mapping to the long_url — small values, trivially shardable across cache nodes by consistent hashing.

  • No invalidation to design: a UrlMapping never changes after creation, so this is one of the rare caches that just needs an eviction policy (LRU is fine) for memory pressure — no TTL is strictly required.
  • The one real risk — a hot key: a single link going viral can overwhelm one cache node while the rest of the cluster sits idle.
  • If link expiration is in scope, that "no TTL" claim needs qualifying: an expired mapping has to stop resolving, so either the cache entry gets a TTL matching the link's own expiry, or every cache hit checks an expires_at field before returning the redirect. The write-once immutability argument still holds — what changes is "does this row still count," not the row's content.

At that scale, the fix is a short-lived, per-instance local cache in front of the shared cache for the handful of keys receiving disproportionate traffic — so one hot key doesn't become a single point of failure.

Key deep dive — recording clicks without slowing down the redirect
FRClick analytics
Thought process
  1. State the constraint plainly first: the redirect has to be fast, no matter what else the system needs to do.
  2. Ask whether recording the click actually needs to happen before the user gets redirected. It doesn't — the user only cares that they land on the right page instantly, not when the click gets logged.
  3. So don't make the redirect wait on it. Hand the event to a queue and return the redirect immediately — the write happens somewhere else, on its own schedule.
  4. Go one step further: batch the downstream writes instead of one row per click. A few seconds of delay in a dashboard is invisible; writing one row per click at high volume isn't free.

If click analytics are in scope, they cannot sit in the redirect's critical path — every added millisecond there defeats the entire point of a URL shortener.

  • Fire-and-forget: write the click event to a lightweight queue and return the 302 immediately. The redirect never waits for that write to finish.
  • Batch downstream: a consumer drains the queue and writes clicks to the analytics store in batches, trading a few seconds of "when a click shows up in a dashboard" for far lower write amplification than one write per click.

The general habit this reflects: the path that has to be fast and correct (the redirect) never waits on a path that only has to be eventually correct (the analytics). Decouple them with a queue rather than making one request do both jobs.

At 10x scale

Once redirects push past 100K/sec, put a CDN in front of the API for anonymous redirects — the 302 response itself is cacheable at the edge, since a given short_code always redirects to the same long_url. The origin only gets hit on a genuine cache miss anywhere across the entire CDN network, not per-request.

Design a Rate Limiter

internal service · sits in the critical path

"Design a service that limits how many requests a client can make in a given window, usable in front of an API." The interesting decisions here are algorithmic, not architectural.

1
Requirements
Functional
  • Allow/deny a request against a per-client limit (e.g. 100 req/min).
  • Configurable per tier.
  • Return 429 + retry-after when exceeded.
Non-functional
  • Negligible added latency — a few ms at most.
  • Correct across many API server instances simultaneously.
  • Must not take the whole API down if its own storage briefly fails.

Worth asking: is the limit per API key, per user, or per IP? Do different endpoints need different limits? We'll assume per-API-key for this walkthrough.

2

  • RateLimitRule (limit, window, scope) — the configured policy, possibly different per tier.
  • RequestCounter (client_id, window_key, count) — the live, fast-changing state checked and incremented on every request.
3
API

Not a public REST API — the interface is a method: allow(client_id) → {allowed: bool, remaining: int, retry_after: seconds}, called by the gateway on every request before it's forwarded anywhere.

Skipped — not pipeline-shaped. Every request is a single synchronous check-and-decide, not a multi-stage transformation.

Every request hits the rate limiter's decision point before the backend ever sees it
← scroll to see the full diagram →
Allowed request
  1. Client sends a request to the API Gateway.
  2. Gateway calls allow(client_id) on the Rate Limiter before doing anything else.
  3. Rate Limiter atomically increments the counter for this client's current window in the Counter Store.
  4. Counter is under the limit → Rate Limiter returns allowed: true.
  5. Gateway forwards the request to the Backend Service as normal.

  2. Counter is at or over the limit → Rate Limiter returns allowed: false with a retry_after.
  3. Gateway short-circuits — the Backend Service is never even called.
  4. Client receives 429 Too Many Requests with a Retry-After header.
Key deep dive — algorithm choice
FRAllow / deny a requestNFRNegligible added latency
Thought process
  1. Start with the simplest possible idea: count requests in a fixed time window, reset the count when the window ends. Cheap, easy to reason about.
  2. Stress-test that idea at the boundary: what happens right at the edge of a window? A burst just before reset, plus a burst right after, sails past the limit completely undetected.
  3. Fix the boundary specifically: instead of a hard reset, slide the window continuously — weight the previous window's count instead of discarding it outright.
  4. Consider a different framing entirely: instead of counting within a window, allow a refillable "budget" — useful when some burstiness is actually fine and shouldn't count as a violation.
  • Token bucket: allows controlled bursts, refills smoothly.
  • Leaky bucket: strictly smooths the output rate.
  • Fixed window counter: simplest, but allows up to 2× the limit right at a window boundary.
  • Sliding window counter: more accurate than fixed window, cheaper than a full request log — usually the practical middle ground.
Illustration — the fixed-window boundary problem (limit: 5/min)23:59:59 → 5 requests (window 1) 00:00:01 → 5 more requests (window 2) = 10 requests in 2 seconds, against a "5/min" limit

The counter itself is shared, high-contention state: use an atomic increment (Redis INCR + EXPIRE, or a Lua script) rather than read-then-write, or concurrent requests can race past the limit.

Key deep dive — the counter as a hot key
NFRCorrect across many instances
Thought process
  1. Ask whether sharding actually solves the traffic problem here. It spreads different clients across nodes — but one single client's own counter still lives on exactly one node, no matter how the cluster is sharded.
  2. Locate the real bottleneck: a client hammering the API sends every one of those requests to the same Redis key — concentrated load that sharding can't fix, only spread other clients around it.
  3. Reconsider what "accurate" needs to mean here. A rate limiter doesn't need to be exactly right — only roughly right, and fast to check.
  4. Use that slack: approximate the count locally and flush to Redis periodically, instead of hitting it on every request — trading a little precision for a large drop in load on one key.

A single popular API key can turn its counter into an extremely hot key — thousands of increments per second hitting one Redis key, on one node, regardless of how many nodes the cluster has. Sharding by client_id spreads different clients across nodes but doesn't help a single client's own counter.

Mitigations
  • Approximate the count locally at the gateway with a short flush interval to Redis, instead of hitting Redis on every single request.
  • Accept slightly relaxed accuracy — a rate limiter doesn't need to be exact, it needs to be roughly right and cheap to check.

This is the same class of problem as a viral link in the URL shortener example — a hot key survives sharding, it doesn't get eliminated by it.

Key deep dive — where in the stack to enforce the limit
FRConfigurable per tierNFRNegligible added latencyNFRSurvives storage failure
Thought process
  1. Notice that "where" is a separate decision from "how" — the algorithm and the physical location of the check answer two different questions.
  2. Consider each layer's actual context: the edge sees raw traffic but knows nothing about the user; the gateway sees the full authenticated request; each service knows its own specific cost.
  3. Realize no single layer is strictly correct — each one protects against a different kind of problem, blunt-force abuse versus precise per-operation cost.
  4. Land on the practical answer: layer more than one — cheap and coarse where traffic first arrives, precise and business-aware closer to where the real cost happens.

The algorithm and the storage matter, but so does where the check happens — that decision changes what it can even protect against.

  • At the edge/CDN: cheapest place to block clearly-abusive traffic before it costs you anything downstream, but has the least context — hard to apply per-user business rules there.
  • At the API gateway: the sweet spot for most systems — one place, full request context, before any backend service has done real work.
  • Inside each service: the most precise option — a specific expensive operation can have a tighter limit than a cheap one — at the cost of implementing and maintaining the same logic in every service.

Most real systems layer more than one of these — a coarse, cheap check at the edge, and a precise, business-aware check at the gateway — rather than picking a single layer.

What happens if Counter Store itself is unreachable is a decision worth stating out loud, not leaving implicit: fail open (let requests through) keeps the API up but briefly loses protection; fail closed (reject everything) protects the backend but turns a cache outage into a full outage. Most systems fail open for a rate limiter specifically — a few seconds of unthrottled traffic is a smaller risk than blocking every legitimate request because Redis hiccuped. Per-tier limits are just a lookup ("what's this client's configured limit") that has to be available at whichever layer above ends up enforcing the check — the tier value itself doesn't change where enforcement happens, it's an input to it.

At 10x scale

If Redis round-trips start showing up in tail latency, push the limiter check into the gateway process itself using a local approximate counter (synced to a shared store periodically) rather than a network call on every request. You trade perfect accuracy for near-zero added latency — usually the right trade for a system whose whole job is to shed load, not account for it precisely.

The pipeline loops on itself — every page fetched can discover new URLs that re-enter the Frontier
← scroll to see the full diagram →
One page's trip through the pipeline
  1. A URL is pulled off the Frontier Queue, chosen from a host-partition that isn't currently rate-limited.
  2. A Fetch Worker downloads the page, respecting that host's crawl-delay policy.
  3. The Parser extracts the page's content and every outgoing link it contains.

Thought process
  1. Start with the obvious approach: check every discovered URL against the database of already-crawled URLs before crawling it.
  2. Stress-test that at scale: billions of URLs means billions of lookups — and most of them will say "not seen" anyway, so most of that cost is wasted.
  3. Ask whether the expensive check is even needed for the common case. It isn't — most discovered URLs really are new; the database round-trip only matters for confirming the rare case.
  4. Add a cheap, fast, in-memory pre-check that can instantly say "definitely never seen" for most URLs, and only fall back to the slow, real check when it's genuinely uncertain.

Checking billions of URLs against a full database on every discovered link doesn't scale — a single Bloom filter check is O(1) and lives entirely in memory.

Illustration — the two-stage checknew URL discovered → Bloom filter says "definitely not seen" → crawl it, no DB hit → Bloom filter says "maybe seen" → check the definitive seen-store
  • The filter isn't the source of truth — it's a cheap gate in front of one, catching the vast majority of "definitely new" links without ever touching the database.
  • False positives ("maybe seen" for a URL that's actually new) are rare and fall back to the real check — the trade-off is memory used by the filter versus queries saved, tuned by the filter's false-positive rate.
Key deep dive — politeness at scale
FRPoliteness / robots.txtNFRResilient to host failures
Thought process
  1. State the actual rule that needs enforcing: don't hit any single host too fast, no matter how many crawl workers are running in parallel.
  2. Notice the risk with many independent workers sharing one queue: nothing stops two different workers from pulling URLs for the same host at the same moment.
  3. Reframe the problem: instead of trusting every worker to remember and coordinate pacing, make violating it structurally impossible — organize the work itself by host.
  4. Partition the queue by host, so a worker literally can't fetch from a rate-limited host — its URLs simply aren't eligible to be pulled yet.

Partition the Frontier by host (or a hash of the host). Each partition owns pacing for its set of domains.

  • The mechanism: workers pulling from a partition enforce a per-host delay before the next fetch to that same host — a worker literally cannot fetch from a rate-limited host because that host's URLs simply aren't eligible to be pulled yet.
  • The bonus: this composes naturally with fault tolerance — if one host is slow or down, its partition backs up without affecting any other host's crawl progress.

Politeness becomes a property of the queue's partitioning strategy, not something bolted on afterward.

Key deep dive — crawler traps and infinite URL spaces
NFRNo infinite loops / duplicate work
Thought process
  1. Notice this is a different problem from duplicate crawling above — that's about re-visiting a URL you've genuinely already seen; this is about a site inventing new-looking URLs faster than you can crawl them.
  2. Recognize a dedupe filter can't catch this alone — every one of those URLs genuinely looks different (a new session ID, a different tracking param), so nothing gets flagged as "already seen."
  3. Attack the root cause instead: most of those "different" URLs are actually the same page, decorated with noise. Strip that noise before the dedupe check even runs, so the filter sees one canonical form.
  4. Add a backstop for whatever normalization can't catch: cap how much crawl budget any single host can consume, so one badly-behaved site can't run away with the whole crawl.

Some sites generate an effectively infinite number of distinct URLs — a calendar page with a "next month" link, or a session ID appended to every link — and a naive crawler will happily follow them forever. This is a different failure mode from the duplicate-crawling deep dive above: that one is about re-crawling a URL you've truly already seen; this one is about a site inventing new URLs faster than you can crawl them, which no dedupe filter alone can catch.

Illustration — normalize before dedupe?sid=8f3a&page=2 → normalize → page=2 ?page=2&sid=91cd → normalize → page=2 (recognized as the same page)
  • Normalize URLs before they ever reach the Dedupe Filter — strip session IDs and tracking parameters, sort query params — so the filter sees one canonical form, not endless variations of the same page.
  • Cap crawl depth and URL count per host, so one badly-behaved site can't consume unbounded crawl budget on its own.

A host whose discovered-URL count grows suspiciously fast relative to its actual content is worth flagging for review rather than trusting the crawler to sort it out on its own.

Key deep dive — extensible crawl priority
FRExtensible crawl priorityNFRBounded storage growth
Thought process
  1. Start from the default: every discovered URL gets crawled and re-crawled on the same schedule, no matter what kind of page it is.
  2. Notice that wastes effort — a news homepage changes hourly, a documentation page might not change for years, but a uniform schedule treats them identically.
  3. Ask what would let the crawler spend its budget where it actually matters: a per-page signal for "how often is this worth re-checking," not a global constant.
  4. Attach a priority score to each Frontier entry and let it drive re-crawl frequency — pages that historically change often get shorter intervals, stable pages get longer ones.

Once a single content-hash comparison on re-crawl isn't enough to justify the fetch cost, a priority scoring pass before pages re-enter the Frontier pays off — pages that change often (news, forums) get shorter re-crawl intervals than pages that rarely change (documentation, archives), so crawl budget goes where freshness actually matters instead of being spent uniformly.

  • The signal is behavioral, not declared: track how often a page's content hash actually changes between re-crawls, and let that history — not a manually assigned category — set its priority.
  • This is also what bounds storage growth: a page that rarely changes gets re-fetched rarely, which caps how much duplicate-content churn the Content Store absorbs over time.

Key deep dive — the concurrency race for the last spot
FRPark a vehicleNFRThread-safe, multiple gatesNFRNo full-spot scan
Thought process
  1. Walk through the naive version step by step: check if the spot is free, then mark it occupied — two separate steps.
  2. Ask what happens if two cars run those same two steps at the exact same instant. Both checks can see "free" before either marking happens — nothing stops that.
  3. Realize the bug isn't in either step alone — it's the gap between checking and acting. Two threads can both pass the check before either one acts.
  4. Close the gap: make check-and-mark a single atomic operation, so no other request can slip in between them.

Two cars can approach the last available spot in the same level at the same instant.

Illustration — check-then-act raceCar A: checks spot → "free" Car B: checks spot → "free" (both pass the check) Car A: marks spot occupied Car B: marks spot occupied → two tickets, one physical spot
  • The fix: make spot assignment atomic — either a lock scoped to the level's free-spot list held across the check-and-mark, or a compare-and-swap on the spot's status field if the runtime supports lock-free atomics.
  • The broader principle: any time two threads can both pass a check before either acts on it, you have this same bug — whether it's a parking spot, a bank balance, or the rate limiter's counter from the earlier example.
  • This is also what avoids scanning every spot: "the level's free-spot list" in the fix above isn't incidental phrasing — each Level maintains its own small set of currently-free spots, so assignment is a lookup against that set, not a scan of every spot's status on every request.
Key deep dive — why these specific patterns
FRCompute fee on exitFRMultiple vehicle typesNFRExtensible without rewrites
Thought process
  1. Before reaching for any pattern, ask what's actually likely to change. For fee calculation, that's the pricing scheme — it shifts far more often than the rest of the parking logic.
  2. For spot status, ask a different question: does behavior genuinely differ by state? Yes — an Available spot accepts a car, an Occupied or OutOfService spot rejects one.
  3. Match the tool to the actual shape of the problem: Strategy for "same operation, different implementation" (fee calc), State for "behavior that depends on which state you're in" (spot status).
  4. Apply the real test before committing to either: does it delete a category of future bug, or is it just vocabulary? If it's just vocabulary, a plain conditional is more honest.
  • Strategy for fee calculation: pricing schemes change more often than the core parking logic — a mall might switch from hourly to flat-rate for an event without anyone touching ParkingLot.
  • State for spot status: a spot's behavior genuinely depends on what state it's in — Available accepts a car, Occupied and OutOfService both reject one — so a state object per status keeps that branching out of ParkingSpot itself, rather than the class filling up with scattered status checks.

The test for reaching for a pattern at all: does it delete a category of future bug, or is it just vocabulary? If a pattern doesn't earn its complexity, a plain conditional is more honest code.

Key deep dive — notifying other systems when availability changes
FRReport availability per level
Thought process
  1. List out who actually needs to know when a spot opens: a sign, an app, maybe a pricing service — more than one, and the list is likely to grow.
  2. Reject the naive option first: having every interested system poll the spot's status on its own schedule works, but "who cares about this" ends up hardcoded, scattered across every one of them.
  3. Flip the direction of the relationship: instead of others repeatedly asking "did it change?", have the spot announce "it changed" once, to whoever's listening.
  4. Recognize the win: ParkingLot never needs to know what a "sign" or an "app" even is — it just publishes changes, and each subscriber decides what to do with them.

A real deployment usually has more than one thing that cares when a spot opens up — a digital sign at the entrance, a mobile app showing live availability, maybe a pricing service that raises rates as a lot fills up.

  • The Observer pattern fits directly: ParkingSpot (or Level) maintains a list of observers and notifies them on every state transition, instead of every interested party polling the spot's status on its own schedule.
  • What it decouples: ParkingLot never needs to know what a "sign" or an "app" even is — it just publishes state changes, and whatever's listening decides what to do with them.

This is the in-process ancestor of the pub/sub pattern used at the service level in the crawler and invoice-search examples — same idea, different scale.

Key deep dive — preventing overselling under distributed contention
FRHold a seatFRConfirm purchaseNFRZero overselling
Thought process
  1. Recognize this is the same shape of bug as the parking lot's race — check then act — just spread across many service instances instead of one process.
  2. Notice why a simple lock doesn't scale the same way here: coordinating a distributed lock across many instances adds real overhead, and a new failure mode — what happens if the lock-holder crashes?
  3. Flip the strategy: instead of asking permission before acting, attempt the write and let the database's own atomicity decide who wins — no lock to coordinate, no lock-holder that can crash mid-hold.
  4. Confirm this actually closes the gap: the conditional write only succeeds if the row still matches the expected state, so two simultaneous attempts can't both succeed — one gets 0 rows affected.

Unlike the parking lot's single-process lock, holds here are checked and set across possibly many Booking Service instances hitting the same inventory row at once. A naive "read status, then write Held" is the same check-then-act race from the parking lot, just distributed.

Illustration — the conditional writeUPDATE seats SET status='held' WHERE id = ? AND status = 'available' → succeeds, 1 row affected → this caller wins the seat → 0 rows affected → someone else already holds it

This is optimistic concurrency: don't ask permission first, attempt the write and let the database's atomicity guarantee reject the losers. It scales better than a distributed lock because there's no lock to hold or release — just one conditional write per attempt.

Key deep dive — the virtual waiting room
FRBrowse / see availabilityNFRSurvives a traffic spike
Thought process
  1. Ask where the actual load comes from during a big on-sale — not from people buying seats, but from far more people just looking.
  2. Recognize that's a fundamentally different problem than the seat-hold correctness fix — you can have a perfectly correct hold mechanism and still get crushed by read traffic before anyone even reaches it.
  3. Reframe the goal: don't try to make the backend handle unlimited simultaneous lookers — control how many people are even allowed to reach it at once.
  4. Admit people to the booking flow at a rate the backend can sustain, and give everyone else something better than a broken page — a queue position.

The actual bottleneck in a ticket on-sale usually isn't the seat-holding logic — it's that far more people want to look at seats than could ever buy one, and all that read traffic can crush the same database the holds depend on.

  • What it decouples: "how many people are interested" from "how many people are actively contending for inventory right now," by admitting buyers to the booking flow at a fixed rate the backend can actually sustain.
  • What everyone else sees: a queue position instead of a broken page.

Same shape as the rate limiter's job, aimed at a different goal: the rate limiter protects a service from too much traffic; the waiting room protects fairness and stability during a spike its designers knew was coming.

Key deep dive — bot and scalper prevention
NFRFair-ish ordering under load
Thought process
  1. Ask whether the concurrency fix — the conditional write — actually solves the fairness problem, not just the correctness one. It doesn't: a script can still win hundreds of individually correct writes faster than any human could click.
  2. Recognize this needs a different kind of defense — not "is this write correct," but "is this behavior even human."
  3. Attack it from multiple angles, since no single check reliably distinguishes a fast human from a script: limit how much one account can hold, add friction at entry, and slow down rapid-fire attempts specifically.
  4. Accept that none of these are airtight alone — a determined bot adapts to any single one — so layer several imperfect defenses instead of chasing one perfect check.

Even a perfectly correct hold-and-purchase mechanism doesn't stop a script from acquiring holds on hundreds of seats faster than any human could click — the concurrency fix prevents overselling, not unfair buying.

  • Per-account purchase limits enforced at the same layer as the seat hold — one account can hold at most N seats for a given event at a time.
  • Friction at the waiting-room entry — a CAPTCHA or proof-of-work check adds just enough cost to make large-scale automation expensive, without meaningfully slowing down a real buyer.
  • Rate limiting the hold endpoint itself per account/IP — the same rate-limiter pattern from earlier in this framework, aimed specifically at slowing rapid-fire hold attempts.

None of these are airtight alone — bots adapt to each one — which is why real systems layer several imperfect defenses rather than searching for one perfect one.

Key deep dive — releasing an expired hold
FRRelease hold automatically
Thought process
  1. State the requirement plainly: a hold nobody completes has to eventually stop blocking that seat for everyone else.
  2. Consider a periodic sweep alone: a background job scans for expired holds and releases them. Ask what happens between expiry and the next sweep — the seat still shows as held even though the hold is already dead.
  3. Consider checking at the point of use instead: before trusting a seat's stored status, check whether its hold has already expired.
  4. Notice neither is complete alone — a lazy check only fires when someone looks at that exact seat again; a sweep alone leaves a staleness window. Run both.

A Hold carries its own expires_at — nothing needs to actively cancel it for the reservation to become logically invalid the moment that time passes.

  • Lazy check on access: whenever a seat's status is read or written, check hold_expires_at first — if it's passed, treat the seat as Available regardless of what the stored status literally says, and update the row opportunistically.
  • Periodic sweep: a background job releases expired holds even for seats nobody's actively querying, so aggregate availability (the browse page) doesn't drift stale indefinitely.

The lazy check keeps the path that matters most — someone requesting that exact seat — instantly correct without waiting on a sweep interval; the sweep keeps everything else roughly honest in the meantime. Same "correctness on the hot path, eventual consistency elsewhere" split as the URL shortener's async click recording.

  2. Recognize the scale question that creates: for a 500-person group, that's 500 individual lookups and pushes per message, a fundamentally bigger job than a 1:1 send.
  3. Consider the simplest option first: push to every online participant immediately. Simple, but the cost at send time now scales directly with group size.
  4. Reconsider for the extreme case: push immediately only to people active recently, and let everyone else catch up on reconnect instead of paying the full fan-out cost upfront every time.

A group message needs the same online/offline delivery decision made independently for every participant, not just one recipient — for a 500-person group, sending is now closer to the fan-out problem than a single message.

  • Fan-out-on-write: look up and push to every online participant's gateway immediately — keeps the read side simple but costs more at send time.
  • Hybrid, for very large groups: push immediately to a subset (e.g. participants active in the last few minutes) and let the rest pull on reconnect.

Same push-vs-pull trade-off as the framework's fan-out glossary entry — a group chat is just a case where "how many recipients" varies by four orders of magnitude between a 1:1 chat and a large group, which is exactly when a fixed strategy stops being the right default.

Key deep dive — no lost messages, correct order

Thought process
  1. Ask what "no message loss" actually rules out: a delivery attempt is allowed to fail — a gateway can crash mid-push — but the message itself must never disappear because of that.
  2. Locate the one step that has to be non-negotiable: the message must be durably written before the system does anything else with it, including trying to deliver it.
  3. Once that's true, delivery becomes a retry problem, not a data-loss problem — a failed push just means try again from the durable copy, not "the message is gone."
  4. For ordering, don't assume it's free: two messages sent close together can arrive at the store slightly out of send order, so ordering needs its own explicit key, not just "whichever wrote first."

Both guarantees come from the same discipline: the Message Store is written to first, before any delivery attempt, and every message gets an ordering key that doesn't depend on when a push happened to succeed.

  • Write before you push: a message is durably persisted the moment it's accepted, before the system attempts the WebSocket push or the offline path. A crashed gateway or a failed push is retried against the durable copy — it never means the message itself was lost.
  • Order by a monotonic key, not wall-clock time alone: a per-conversation sequence number (or a timestamp with a tie-breaking id) survives clock skew and near-simultaneous sends; sorting purely by sent_at from different servers can't guarantee that.

Same instinct as Ticketmaster's seat hold and the URL shortener's click recording: identify the one write that has to be correct and durable, and let everything after it — delivery, retries, display — be the part that's allowed to be eventually consistent.

The full journey — from search to a confirmed booking

Worth heading off directly: why not a status column on Room, the way Ticketmaster flags a seat Available or Held? A seat has exactly one state at a time — the column is the answer. Steps 3 & 4 — check and write: one fork, not six options

These were named as separate steps above, but "how do we check fast" and "how do we prevent a conflict" aren't independent choices — which one you use for the check determines what you need for the write. It's one fork, then one complete path to follow, not a checklist of every technique.

The fork

Does your database support a native exclusion constraint for overlapping ranges (Postgres's EXCLUDE, or an equivalent)?

Yes → Path A

One constraint on the table. Done — no separate index for this query, no SERIALIZABLE, no lock. The database is the whole guarantee.

No → Path B

An index for the fast check, a conditional insert for the write, and one guard (SERIALIZABLE or a lock) wrapped around it — three pieces, working together.

Either path, optionally: layer an in-process tree on top for one genuinely hot room — that part is the same regardless of which path you're on, detailed at the end.

Path A — the EXCLUDE constraint (recommended, on Postgres)

A database-enforced rule: no two bookings for the same room may have overlapping ranges. Its own index handles the fast check too — this is the entire path, nothing else in this deep dive needs to be added on top of it.

Illustration — the constraint, and the ordinary insert it protectsCREATE TABLE bookings ( id SERIAL PRIMARY KEY, room_id INT NOT NULL, during TSRANGE NOT NULL, EXCLUDE USING GIST (room_id WITH =, during WITH &&) ); The write is a completely ordinary insert — no WHERE, no NOT EXISTS: INSERT INTO bookings (room_id, during) VALUES (:room_id, tsrange(:start, :end)); If a row already exists for this room whose "during" range overlaps — Postgres REJECTS the insert outright, atomically, at the storage engine level. No SERIALIZABLE isolation, no lock required — the guarantee is built into the schema, enforced the same way a UNIQUE constraint is. Two bookers, same slot, same instant: one INSERT succeeds, the other fails with a constraint violation — the database decided who won, not the app.

Why this is the recommendation, not just one option among several: it protects you even if a future developer writes a careless query, since the guarantee lives in the table, not in any one statement someone has to remember to write correctly every time.

Path B — index, conditional insert, and a guard (when EXCLUDE isn't available)

Three pieces that only work together — an index makes the check fast, a conditional insert bundles the check into the write, and one guard closes the race the conditional insert alone can't.

1 — the index
Illustration — the B-tree index, and the query it speeds upCREATE INDEX idx_bookings_room_start ON bookings (room_id, start_time); SELECT 1 FROM bookings WHERE room_id = :room_id AND start_time < :end AND end_time > :start; → the index narrows this to rows for the right room, near the right time — fast, but still just a SELECT. Two concurrent transactions can both run it, both see zero rows, and both then insert. The index makes the check fast; it does nothing to prevent the race below.
2 — the conditional insert

Ticketmaster's fix doesn't transfer as-is: a seat is one row with one status flag — a single conditional UPDATE is enough. A room's calendar has no single row to flip, so the check-across-many-rows and the insert have to happen as one atomic step — the pattern commonly called a conditional insert, the insert-side counterpart to Ticketmaster's conditional update.

Illustration — INSERT … WHERE NOT EXISTSINSERT INTO bookings (room_id, start_time, end_time, organizer_id) SELECT :room_id, :start, :end, :organizer_id WHERE NOT EXISTS ( SELECT 1 FROM bookings WHERE room_id = :room_id AND start_time < :end AND end_time > :start ); → one statement: the check and the insert happen together, not two round trips

Still not automatically safe on its own — a building block, not the complete guarantee. At the commonly-default READ COMMITTED isolation level, two concurrent transactions can both evaluate NOT EXISTS against the same pre-insert snapshot, both see "nothing conflicts," and both insert. Piece 3 is what actually closes this.

3 — the guard: pick exactly one
Illustration — the race this guard closesBooker A: checks [10:30, 11:30) → free Booker B: checks [10:30, 11:30) → free (both pass the check) Booker A: writes the booking Booker B: writes the booking → double-booked, same room, same slot
SERIALIZABLE isolation — optimistic

Run the conditional insert inside a transaction at SERIALIZABLE isolation. Neither booker locks anything upfront — both proceed as if uncontended, and the database catches the real conflict at commit time, aborting one.

  • No explicit locking code — the database enforces it.
  • The loser gets a serialization error and has to retry, which the app must handle.
  • Costs more under real contention.
An explicit lock — pessimistic

Acquire a lock scoped to the room before the check-and-insert, held until the transaction ends — assume contention and prevent it upfront. Two ways to take it, below.

  • Only bookers on the same room ever wait on each other.
  • Simpler to reason about — the second booker just waits its turn.
  • Must be released on every code path, including a crash, or it becomes its own outage.

Why not a Redis lock instead of either of these? Because the lock and the write it protects would live in two separate systems — if the app crashes between acquiring a Redis lock and committing to Postgres, the lock needs a TTL to self-clean, and that TTL becomes its own tuning problem. Both mechanisms above live inside the same transaction as the write — Postgres releases the lock automatically the instant that transaction ends, crash or not, with nothing to tune. Redis earns its place coordinating something that spans more than one database transaction, not for guarding one insert Postgres can already guard for free.

Two ways to take that lock
Advisory lock — an arbitrary token

pg_advisory_xact_lock(room_id) — Postgres-specific. Locks a number that means "room 101" only by convention; works against any schema, needs no existing row to lock.

SELECT ... FOR UPDATE — the actual row

Standard SQL, portable beyond Postgres. Locks a real row in the rooms table — the thing the contention is actually about, not a synthetic hash standing in for it.

Illustration — the advisory lock, traced across two bookersBEGIN; SELECT pg_advisory_xact_lock(:room_id); -- acquire FIRST, before checking INSERT INTO bookings (room_id, start_time, end_time, organizer_id) SELECT :room_id, :start, :end, :organizer_id WHERE NOT EXISTS ( SELECT 1 FROM bookings WHERE room_id = :room_id AND start_time < :end AND end_time > :start ); COMMIT; -- lock releases automatically, tied to the transaction Booker A: BEGIN → lock(101) acquires instantly → check+insert → COMMIT (released) Booker B: BEGIN → lock(101) BLOCKS, waiting — B's query hasn't even run yet ...the moment A commits... B's lock acquires → check+insert now correctly sees A's booking → 0 rows affected → app tells B "someone got it first" B never raced A — B's check didn't start until A's transaction had already finished. That's the actual difference from SERIALIZABLE: the lock prevents the interleaving, rather than catching it afterward. Caveat: pg_advisory_xact_lock takes a bigint, so a UUID/string room_id is hashed down first — a hash collision means two different rooms could occasionally, harmlessly wait on each other.
Illustration — SELECT ... Between the two locks, concretely: FOR UPDATE if you need this to run on a non-Postgres database too, or you want a deleted/mistyped room_id caught in the same round trip that acquires the lock, instead of a silent no-op. The advisory lock if what you're protecting isn't tied to one row at all — locking a whole floor for a bulk operation, or a business rule keyed on something that spans tables — where there's no single row to lock against in the first place. A plain UNIQUE constraint on (room_id, start_time) is worth adding either way, as a cheap backstop against the exact-duplicate case — the same room, the same exact start time, submitted twice. It won't catch a genuine partial overlap (10:00–11:00 against 10:30–11:30) the way EXCLUDE does — a narrower guarantee, but one available on databases that don't support range exclusion at all.

Escalation — an in-process tree, on top of either path

Not a third path — an optional speed layer for one genuinely hot room (a popular shared space, an all-hands room), sitting in front of whichever path above is doing the actual guaranteeing.

  • Materialize on write: generate every instance of the series up front. Simple to query, but wasteful — a weekly meeting "forever" means either an arbitrary cutoff or unbounded storage, and changing the series means rewriting every future instance.

Thought process
  1. Start with the most direct-sounding idea: fan a search request out to all 30+ product databases and merge whatever comes back.
  2. Trace what happens to latency: the response can only be as fast as the slowest of 30+ independent calls — with that many in flight, something is always slow.
  3. Trace what happens to ownership: each product team now has to build and maintain search capability on their own schema, for a use case they don't actually own.
  4. Realize the fix isn't "make the fan-out faster" — it's not fanning out at query time at all. Separate the write side (30+ databases, unchanged) from a single purpose-built read copy that every search hits instead.

The naive approach — fan a search request out to all 30+ product databases and merge the results — fails for reasons that compound as the product count grows.

  • Tail latency amplification: the response is only as fast as the slowest of 30+ services on that request — with enough independent calls, something is always slow.
  • Permanent coupling: each product team now has to expose and maintain ad hoc search/filter capability on their own schema, for a use case they don't own.
  • Schema fragmentation: 30+ teams' slightly different ideas of "customer" or "amount" turn a simple query into a fragile integration problem, repeated 30+ times.
  • Grouping gets hard too: merging and grouping 30+ separate, differently-shaped result sets into one "Product A / Product B / …" view is real work, done on every single search.

The fix is CQRS: separate the write model (30+ independently-owned databases) from the read model (one denormalized, purpose-built search index). Reads never touch the write side at query time — and since every product's data already lives in the same index with the same shape, grouping by product is a trivial reshape of one result set, not a live merge of 30+.

FROnly subscribed products in resultsFRLapsed subscriptions still findableNFRSubscription changes take effect immediately
Thought process
  1. Start with the obvious-seeming fix: bake a product_id IN (…) filter into the search query itself, scoped to whatever the caller is subscribed to.
  2. Trace the side effect of that choice: the query's result now depends on who's asking, not just what they typed — two users searching identical text get different results.
  3. Connect that to the caching work already done: a result that differs per user can't be cached once and shared — the key has to become (user, query), which is exactly the key-space explosion already ruled out.
  4. Move the filter instead of removing it: let the text-match stay caller-blind and shareable, then apply the subscription filter to that (usually small) result afterward, on every single request, cache hit or miss.

Different users subscribe to different subsets of the 30+ products, a subscription change has to take effect immediately, and losing access to a product shouldn't erase the ability to find invoices from when access was active — all while the search cache itself has to stay shared, not per-user, or it collapses under real traffic (see the Caching Playbook).

  • Cache the subscription history separately, keyed by user: it changes rarely relative to how often a user searches, so this specific lookup — user_id to product list — is cached (Redis, short TTL). Design a News Feed

fan-out-on-write vs. fan-out-on-read · the celebrity problem

"Design a system where a user posts content, and anyone following them sees it in their home feed." A read-heavy, write-light system on the surface — but the follower graph is wildly uneven: most accounts have a few hundred followers, a handful have tens of millions. Any design that assumes uniform fan-out breaks on that handful.

1
Requirements
Functional

  • Follow and unfollow other users.
  • View a home feed — a merged, reverse-chronological stream of posts from everyone you follow.
  • Paginate through the feed without seeing duplicate or missing posts as new content arrives while scrolling.
Non-functional
  • Feed loads fast (low hundreds of ms) even for a user following thousands of accounts.
  • Posting must not get slower or block based on how many followers the poster has — a celebrity's post can't take minutes to "finish."
  • New posts should reach followers' feeds within seconds, not necessarily instantly.
  • Storage for materialized feeds can't grow without bound per user.

  • Follow (follower_id, followee_id) — the graph edge; who follows whom.
  • Post (id, author_id, content, created_at) — the source of truth for content, written once.

Key deep dive — fan-out-on-write vs. fan-out-on-read, and the celebrity problem
FRView home feedNFRFeed loads fastNFRPosting isn't follower-count-dependent
Thought process
  1. Start with the option that makes reads trivially fast: precompute every user's feed at post time, so a read is just "fetch my already-built list."
  2. Stress-test it against the extreme case: an account with 50 million followers posts. That's 50 million writes triggered by one action — the post "hangs" while fan-out grinds through a queue, or the write path itself gets dragged into that cost.
  3. Try the opposite extreme instead: don't precompute anything, merge the feed live from everyone the reader follows at read time. Test it against the common case — a normal user following 300 accounts now does a 300-way merge on every single feed load.
  4. Notice neither extreme is right for both kinds of accounts, because the actual variable is follower count, which spans many orders of magnitude. Split the strategy by that number instead of picking one for everyone.

The two pure strategies are each right for a different, common case — the fix is choosing per-author, not picking one architecture for the whole system.

  • Fan-out-on-write (push): write a Timeline entry to every follower's feed the moment someone posts. Reads become a single fast lookup — the cost is paid once, at write time, and shared across every future read of that feed.
  • Fan-out-on-read (pull): store nothing extra; merge posts from followed accounts live, at read time. Writes stay cheap and instant regardless of follower count — the cost is paid on every single read instead.
  • The hybrid: fan-out-on-write for accounts under a follower threshold (the overwhelming majority), fan-out-on-read for the small number above it. A normal user's feed is a fast Timeline Store lookup; a celebrity's posts are picked up live by the read path, merged in only for the followers actually reading their feed right now.

This is the same instinct as Uber's location pings getting their own storage path separate from ride records — identify the one input whose scale characteristics are wildly different from everything else, and give it a different path instead of forcing one design to survive both extremes.

Key deep dive — keeping the materialized timeline bounded
NFRStorage can't grow unbounded per user
Thought process
  1. Notice fan-out-on-write has a quiet cost the read-speed win doesn't mention: every follow relationship now implies a growing set of stored rows, forever, for every active user.
  2. Ask how much of that stored history actually gets read. Almost none of it — people scroll back a few dozen or hundred posts, essentially never to the bottom of a feed that's years old.
  3. Notice the asymmetry: paying storage cost for content that's rarely if ever read is waste, not correctness.
  4. Cap it deliberately: keep only the most recent N entries materialized per user, and treat anything older as reconstructible on demand rather than permanently stored.

A Timeline Store entry exists for every (follower, post) pair from a fanned-out write — for an active user following hundreds of accounts, that's an unbounded, ever-growing list with no natural cap.

  • Cap each user's materialized timeline to the most recent N entries (a few hundred to a couple thousand) — old entries are trimmed, not kept forever.
  • Falling off the cap isn't data loss: Posts DB is still the source of truth. A user who scrolls past the materialized window falls back to a live, fan-out-on-read-style query for anything older — rare enough in practice that it doesn't need to be fast.

Same shape as the crawler's bounded storage growth — cap the common, fast path deliberately, and let the rare, slow path fall back to the source of truth instead of trying to make everything permanently fast.

Key deep dive — pagination that stays correct while new posts keep arriving
FRPaginate without duplicates/gaps
Thought process
  1. Start with the obvious pagination approach: page 1 is the first 20 rows, page 2 is the next 20, using offset and limit.
  2. Trace what happens if three new posts arrive between loading page 1 and page 2: everything shifts down by three. Page 2, requested by offset, now starts three rows earlier than the reader expects — the last three posts they already saw on page 1 repeat.
  3. Notice the real problem: an offset is a position in a list that's actively changing underneath the reader, not a stable reference to anything.
  4. Reference content instead of position: ask for "everything older than the last post I actually saw," not "whatever's at position 20 right now."

A naive offset-based page ("give me results 21–40") silently breaks the moment new posts land between two page loads — everything shifts, and the reader sees duplicates or skips posts entirely.

Illustration — offset breaks, cursor doesn'tPage 1 loaded: posts ranked 1-20 (newest first) 3 new posts arrive Page 2 by OFFSET 20: now shows what used to be ranks 18-37 → 3 duplicates Page 2 by CURSOR (oldest post_id/timestamp shown on page 1): "give me posts older than that" → always correct, regardless of what's arrived since
  • Cursor-based pagination: the cursor is the timestamp (or id) of the last post shown, not a row count. "Older than this" is a stable reference no matter how many new posts have landed since.
  • The merged-source complication: since a page can be assembled from both the Timeline Store and a live celebrity check, the cursor has to be comparable across both — a plain timestamp works for this; an opaque per-source offset would not.

This is a narrow instance of a general rule: any paginated view over data that changes while it's being read needs a stable reference point, not a position — the same reason a database cursor scans by key, not by row number.

Design Collaborative Document Editing

operational transformation · concurrent edits, no losers

"Design a system where multiple people can type into the same document at the same time, and everyone converges on the same result." Every other worked example on this page solves contention the same way — one actor wins, everyone else is rejected and retries. This one is the opposite shape: two people typing in the same paragraph at the same instant both succeed, and the system's whole job is making their edits merge into something coherent, not picking a winner.

1
Requirements
Functional
  • Multiple users edit the same document simultaneously; every keystroke is visible to everyone else within roughly a second.
  • Every collaborator's editor eventually shows the exact same document content — no permanent divergence.
  • A user who was offline (laptop closed, network drop) can reconnect and have their local edits merged in, not discarded.
  • Cursor position and text selection are preserved correctly for a user even while someone else's edit lands above them in the document.
Non-functional
  • Local edits feel instant — a keystroke must never wait on a round trip to the server before appearing in the typer's own editor.
  • Convergence: given the same set of edits, every client ends up with identical document content, regardless of the order edits were received in.
  • No edit is ever silently dropped, even under concurrent, conflicting edits at the same document position.
  • Reconnecting after an extended offline period doesn't require re-downloading the whole edit history.

Worth asking: rich text (bold, formatting, embedded images) or plain text? We'll design for plain text — insert/delete on a character sequence. Rich formatting is the same core algorithm with a richer operation set, not a different architecture.

2
Core Entities
  • Document (id, content, revision) — the current text and a monotonic version number; revision is what every operation is transformed against.
  • Operation (doc_id, client_id, base_revision, type, position, value) — a single insert or delete, tagged with the revision it was created against, not the revision it lands on.
  • Session (client_id, doc_id, connection_state) — one collaborator's live connection to a document.
3
API

Not a request/response API in the usual sense — a persistent connection carrying a continuous operation stream in both directions:
→ send: {type: insert|delete, position, value, base_revision} — a local edit, the moment it happens
← receive: {op, transformed_against: revision} — another collaborator's edit, already transformed to apply cleanly to this client's current state
GET /docs/{id}/snapshot → current content + revision, for a client joining or reconnecting

4
Data Flow — genuinely earns its place here
  1. A user types; the character is applied to their local editor state immediately — before any network round trip.
  2. The edit is sent to the server as an operation tagged with the revision the client was looking at when they made it.
  3. The server transforms the incoming operation against every operation it has received since that base revision, producing a version that applies cleanly to the current server state.
  4. The transformed operation is applied to the server's document and broadcast to every other connected client, each of which transforms it again against their own local pending edits before applying it.
5
High-Level Design

Every client keeps a full local copy of the document and applies its own edits instantly; the server's job is transforming and ordering, not being the only place edits happen — diagrammed below.

6
Deep Dives

  2. The operation is sent to the Transform Server, tagged with the revision A's copy was at when the edit was made.
  3. The server transforms it against any operations received since that revision (from other clients), producing a version that applies cleanly to the server's current state.

  3. B's operation, still tagged base_revision=41, gets transformed against A's now-applied edit — its position is adjusted to account for A's insertion — then applied as revision 43.
  4. Both A and B end up with identical final content: A sees B's transformed edit arrive; B's own local copy already applied its edit and now reconciles against A's, arriving in the other order but converging on the same text.
Key deep dive — why last-write-wins and locking both fail here
FREdit simultaneouslyNFRNo edit silently droppedNFRConvergence
Thought process
  1. Reach for the pattern that's worked everywhere else on this page: when two writers conflict, let one win. Try applying it here — the server keeps whichever edit arrives last.
  2. Trace what "arrives last" actually does to the loser: it doesn't get rejected and retried like a failed seat hold — it's just gone. The user who typed it sees their own words vanish.
  3. Try the other classic fix instead: lock the document, or the paragraph, while someone's editing it. Test it against how people actually use a shared doc.
  4. Notice locking doesn't solve concurrent editing, it prevents it — the whole premise of the product is that two people type in the same document at once, and a lock makes one of them wait.

Every other worked example on this page resolves contention by making one writer win and rejecting the rest — a seat hold, a parking spot, a ride acceptance. Try that same instinct here and it breaks the product's actual premise.

  • Last-write-wins silently destroys work: if the server just keeps whichever operation arrives last, the other user's edit isn't rejected-and-retried the way a failed conditional write is — it's discarded outright, with no signal to anyone that it happened.
  • Locking prevents the actual use case: a pessimistic lock on a paragraph or the whole document stops the exact behavior the product exists for — two people typing in the same place at once.
  • The reframe: this isn't a contention problem with one correct winner. It's a merge problem — both edits are valid, and the system's job is producing one document that reflects both, not picking between them.

That reframe is the whole reason this example doesn't fit the "atomic conditional write" pattern from Ticketmaster, Uber, and the parking lot — there's no single row to guard, because there's no single correct outcome to guard it toward.

Key deep dive — operational transformation, the actual mechanism
FRInstant local editsNFRConvergenceNFREdits feel instant
Thought process
  1. Restate the actual goal precisely: two edits made against the same starting document, in some order, should produce the same final document regardless of which order they're applied in.
  2. Notice naively applying both edits at their original positions doesn't do that — an insertion earlier in the text shifts every position after it, so the second edit's original position is now pointing at the wrong place.
  3. The fix has to adjust the second operation's position based on what the first operation actually did — not apply it blindly, and not discard it.
  4. Formalize that adjustment as a function: given two concurrent operations, transform one against the other so it still does what the user intended, on top of the other's result.

Operational Transformation (OT) is the algorithm Google Docs actually uses — not CRDTs, despite that being the more commonly cited answer in interviews. The core idea: don't just apply a remote operation as-is — adjust it based on what's changed locally since it was created.

Illustration — why a raw position breaks, and what transform fixesStarting text: "HELLO WORLD" (revision 41) Client A inserts "X" at position 5 → "HELLX O WORLD" (their local view) Client B inserts "Y" at position 8 → "HELLO WOYRLD" (their local view) Server applies A first: "HELLX O WORLD" is now revision 42. B's op says "insert Y at position 8" — but position 8 in the OLD text is no longer position 8 now that A inserted a character before it. transform(B's op, against A's applied op): A inserted before B's position → shift B's position right by 1 → insert "Y" at position 9 → "HELLX O WOYRLD" (correct, on both sides)
  • The transform function is the whole algorithm: given two operations that both started from the same revision, produce an adjusted version of one that, applied after the other, yields the same result no matter the order — this property is what convergence actually means, made concrete.
  • Every client re-derives this, not just the server: when Client A receives B's operation, A also transforms it — against A's own pending local edits — before applying it locally. The server and every client are running the same transform logic independently.
  • This is why edits feel instant: a client never waits for the server's permission to show a keystroke — it applies locally first, and reconciles with the server's transformed version afterward, in the background.

CRDTs solve the same convergence problem with a different trade-off — no central transform step, but a data structure with more per-character metadata overhead. OT keeps the document itself lightweight at the cost of needing a server (or an agreed-upon peer) to do the transforming — the right trade-off for a product where a server's already in the loop for storage and access control anyway.

Key deep dive — offline edits and reconnection
FROffline edits merge on reconnectNFRNo full re-download on reconnect
Thought process
  1. Ask what actually changes when a client goes offline for a while: nothing about the transform logic — the gap is just "how many operations happened while this client was gone."
  2. Consider making the client re-fetch the whole document on reconnect. Test it against a long meeting-room doc with hours of edit history — that's a lot of data for what might be a five-minute gap.
  3. Notice the client already has almost everything — its own last-known revision and its own queued local edits. What it's actually missing is just the delta.
  4. Treat reconnection as "catch up on what you missed," not "start over" — replay only the operations since the client's last known revision, transformed against each other the same way live concurrent edits already are.

A client that was offline is really just a client whose last-known revision is far behind — the same transform mechanism that handles two people typing a second apart handles someone reconnecting after an hour, just with more operations to transform against.

  • The client queues its own edits locally while offline — they're still applied instantly to its local copy, exactly as if the server were reachable, just not yet sent anywhere.
  • On reconnect, the client sends its queued operations tagged with its last-known revision — the server transforms the entire queued batch against everything that happened since, the same operation used for any concurrent edit, just applied more times in a row.
  • The Operation Log doesn't need to be replayed from the beginning: a periodic snapshot in Document Store means "catch up" only needs operations since the last snapshot before the client's revision, not the document's entire history.

Treating "offline for an hour" as a large version of the same problem as "offline for a millisecond between two keystrokes" is what keeps this from needing a separate reconciliation system — it's the identical transform, run more times.

Design Multiplayer Game State Sync

client-side prediction · server reconciliation · lag compensation

"Design the system that keeps every player's view of a fast-paced multiplayer game (a shooter, a racer) in sync, despite each player having a different, constantly-changing amount of network lag to the server." Every other real-time example on this page treats the server's word as final the moment it arrives — a message is delivered, an operation is transformed and applied. This one is different: the client is deliberately allowed to be wrong for a fraction of a second, on purpose, because waiting for the truth would feel worse than briefly guessing.

1
Requirements
Functional
  • A player's own movement responds instantly to their input, regardless of their connection latency to the server.
  • Every player sees every other player's position and actions, converging on one consistent game world.
  • The server is the final authority on outcomes — did a shot land, is a player actually where they claim to be.
  • A cheating or malfunctioning client cannot force an outcome the server wouldn't otherwise allow.
Non-functional
  • Input-to-screen latency for a player's own actions must feel instant (well under 50ms) even when their real round trip to the server is 150ms or more.
  • The game must stay playable and fair for players with meaningfully different latencies to the same server, at the same time.
  • State updates for a fast-moving match (dozens of players, tens of updates per second each) can't saturate available bandwidth.
  • A brief network hiccup should degrade gracefully — a stutter, not a disconnect.

Worth asking: authoritative server, or peer-to-peer with one player's client as host? We'll assume a dedicated authoritative server — it's the only model that satisfies "a client can't force an outcome," which most competitive real-time games require.

2
Core Entities
  • PlayerState (player_id, position, velocity, tick) — the authoritative truth for one player, as of a specific server tick.
  • Input (player_id, sequence_num, keys_pressed, client_tick) — one frame of a player's raw input, tagged with a number the client can later match against the server's response.
  • WorldSnapshot (tick, player_states[]) — the full authoritative game state at one server tick; what the server actually reasons about and what it broadcasts.
3
API

A persistent connection carrying continuous, small, frequent messages in both directions — not a request/response API:
→ send: {sequence_num, keys_pressed, client_tick} — a player's input, sent roughly every frame
← receive: {tick, player_states[], last_processed_sequence_num} — the authoritative world snapshot, broadcast at a fixed server tick rate
The last_processed_sequence_num is what lets a client know which of its own predicted inputs the server has already accounted for.

4
Data Flow — genuinely earns its place here
  1. A player presses a key; the client applies its effect to its own local view immediately, and separately sends the raw input to the server.
  2. The client keeps every unacknowledged input it's sent, in order, in a small local buffer.
  3. The server receives inputs from every player, advances the authoritative simulation by one tick, and broadcasts the resulting world snapshot to everyone.
  4. Each client receives the snapshot, discards any of its own buffered inputs the server confirms it already processed, and replays whatever inputs are left on top of the server's authoritative position — correcting its local prediction if it was wrong.
5
High-Level Design

Client and server run the same simulation in parallel, deliberately out of sync by design — the client races ahead on guesses, the server catches it up to the truth — diagrammed below.

6
Deep Dives

Three below: (a) client-side prediction and server reconciliation, (b) lag compensation for hit detection, and (c) keeping state updates bandwidth-cheap.

Every client predicts its own movement instantly and reconciles against the server's periodic authoritative snapshot. Hit detection is the one place the server looks backward — rewinding to what the shooter actually saw, not what's true on the server right now.
A player moves (the common case)
  1. Player A presses a movement key; the client applies it to A's local view immediately and stores the input in a local buffer, tagged with a sequence number.
  2. The same input is sent to the Game Server, which won't process it until the next tick — A's screen is already ahead of what the server has seen.
  3. The server advances its simulation and broadcasts a snapshot including the last input sequence number it processed for A.
  4. A's client discards buffered inputs up to that sequence number, then replays any newer ones (sent since) on top of the server's confirmed position — correcting itself if its guess was wrong, ideally by an amount too small to notice.
Player D shoots at Player C (lag compensation)
  1. D's screen is showing C's position from roughly D's round-trip-time ago — everything D sees is already slightly in the past.
  2. D fires at where C appears to be; the client sends the fire event with the client_tick D was looking at.
  3. The server, instead of checking against C's current authoritative position, rewinds its short tick history to that earlier tick and checks the shot against where C actually was then.
  4. If it would have hit at that moment in the past, the server counts it as a hit — from D's perspective, the shot they saw land actually lands, even though the server's "right now" state has already moved on.
Key deep dive — client-side prediction and server reconciliation
FROwn movement responds instantlyNFRInput-to-screen latency <50ms
Thought process
  1. Start from the naive, "obviously correct" design: the client sends input, waits for the server's response, and only then updates what the player sees.
  2. Compute what that actually costs a player with 150ms round-trip latency: every keypress takes 150ms to even start appearing on screen. In a fast-paced game, that reads as broken, unresponsive controls.
  3. Realize the fix isn't making the network faster — it's not waiting on it at all for the player's own actions. Apply the input locally, immediately, as a guess.
  4. A guess can be wrong, so there has to be a way to correct it cheaply when the server's real answer arrives — replay whatever's changed since, instead of discarding and restarting.

Waiting for a server round trip before showing the effect of your own keypress is the naive design — and it's the one thing this system cannot do, no matter how it's built.

  • Client-side prediction: apply input to the local simulation the instant it happens, without waiting for the server. The player's own actions always feel instant, because they are — the client isn't waiting on anything.
  • Server reconciliation: when the authoritative snapshot arrives, it may say the player ended up somewhere slightly different than the client guessed — maybe they clipped a wall the client didn't account for. The client discards its confirmed-processed inputs and replays only the unconfirmed ones on top of the server's real position, correcting the small error.
  • Why this doesn't look like OT's client/server split: in the collaborative-editing example, the server transforms and every valid edit survives — there's no "wrong" outcome, only different orderings. Here the server can flatly overrule the client's guess. Prediction is a UX technique for hiding latency, not a claim that the client's guess was also valid.

The correction is usually invisible: most of the time the client's guess and the server's real answer match closely enough that "replay the last few inputs" produces no visible snap — it only becomes noticeable under packet loss or a genuinely surprising interaction (another player blocking a path the client didn't know about yet).

Key deep dive — lag compensation for hit detection
FRServer is final authority on outcomesNFRFair across different latencies
Thought process
  1. State the naive rule plainly: when a shot is fired, check it against the target's current position on the server, right now.
  2. Realize "right now" on the server and "what the shooter actually saw" are two different moments — the shooter's screen was already showing a slightly-past position because of their own latency.
  3. Trace the consequence: a shot that looked, on the shooter's own screen, like it clearly landed gets called a miss, because by the time it reached the server the target had already moved past that point.
  4. Fix the mismatch directly: don't check the shot against the present. Check it against the exact moment the shooter was actually looking at, using history the server already has.

The naive rule — check a shot against the target's current server-side position — is fair in theory and infuriating in practice, because "current" on the server isn't what the shooter was actually looking at.

Illustration — why the server rewindsD's round-trip latency: 100ms D sees C's position as of: server_tick - 100ms (always slightly stale) D fires at what looks, on D's screen, like a clean hit on C.   • The server keeps a short rolling history of recent world states — just long enough to cover the highest latency the game tolerates, not the whole match.
  • Every fire event carries the client's tick, so the server knows exactly which moment in its own history to rewind to before checking the shot.
  • The trade-off this creates: from the target's perspective, they can be shot after they've already ducked behind cover on their own screen — "shot behind the wall" is the well-known player complaint this technique causes, in exchange for shots that feel fair to the person pulling the trigger.

There's no version of this that's fair to both players simultaneously — favoring the shooter (rewind) or favoring the target (no rewind) are both defensible defaults, and most competitive shooters pick the shooter, because a miss that looked like a hit reads as more broken than a hit that looked like a miss.

Key deep dive — keeping state updates bandwidth-cheap
FREvery player converges on one worldNFRDoesn't saturate bandwidthNFRGraceful degradation on hiccup
Thought process
  1. Start with the simplest broadcast: send every player's full state to every other player, every tick.
  2. Compute the cost as player count grows: the data sent per tick grows with the square of the player count — everyone's full state, to everyone — and most of that data hasn't actually changed since the last tick.
  3. Notice most of any given tick is redundant: a player standing still sends the same position over and over, identical to the last update.
  4. Send only what changed since the last tick a given client has already acknowledged, instead of the full state every time.

Broadcasting every player's complete state to every other player, every tick, scales quadratically with player count and wastes most of its bandwidth on data that hasn't changed since the last tick.

  • Delta compression: send only the fields that changed since the last snapshot the receiving client has acknowledged — a stationary player contributes almost nothing to that tick's payload.
  • Interpolation on the receiving end: other players' positions are deliberately rendered slightly in the past (a small buffer, e.g. 100ms behind), smoothly interpolated between the last two received snapshots — this hides the gaps between discrete network updates as smooth motion, instead of visible teleporting.
  • Graceful degradation: a brief dropped packet just means one tick's delta is missing — the next tick's delta is computed against the last state the client actually has, so a short hiccup causes a small stutter, not a desync that needs a full resync.

Prediction hides latency for a player's own actions; interpolation hides latency for everyone else's — the same underlying problem (the network is never instant), solved with the opposite technique depending on whether the player controls what they're looking at.

Design a Video View Count System

approximate counting · write batching · bot resistance

"Design a system that counts and displays view counts for videos, at a scale where a single popular video can be viewed millions of times an hour." It reads like a trivial counter — count = count + 1 — until the volume makes that literal implementation impossible, and the count itself becomes a target worth gaming. The interesting design decision isn't how to count; it's how precise the count actually needs to be, and what's allowed to lag behind reality in exchange for surviving the write volume.

1
Requirements
Functional
  • Record a view whenever a user watches a video past some minimum threshold (not just loading the page).
  • Display a view count on the video, visible to anyone.
  • Support both a single popular video (millions of views/hour) and millions of unpopular videos (near-zero traffic) in the same system.

No step between a view and the stored count is a per-view database write. Events are aggregated in memory and flushed as batched increments — the displayed count is always a few seconds to a minute behind reality, on purpose.
Write path (a view happens)
  1. Playback crosses the minimum watch-time threshold; the client fires a view event to the Event Queue and moves on — no response is waited for.
  2. The Stream Processor consumes events in small windows, deduplicating by viewer/session and discarding events that don't pass basic validation.
  3. Valid events increment an in-memory counter for that video — for a hot video, one of several shards of that counter, not a single shared number.
  4. Every few seconds, each counter's accumulated delta (not its running total) is flushed to the View Count Store as one batched increment — thousands of individual views can collapse into a single write.
Read path (viewing a count)
  1. A reader loads a video page; the displayed count comes from Cache, not a live read of the View Count Store.
  2. Cache is refreshed on a short interval (seconds, not sub-second) from the store's latest aggregated total, including summing any active shards for a hot video.
  3. The number shown is always slightly behind the true count — by design, not by accident — trading exactness for a read path that never touches a write-heavy store directly.
Key deep dive — why a database increment per view doesn't survive real traffic
FRPopular + unpopular videos togetherNFRNever adds latency to playbackNFRNo hot-key bottleneck
Thought process
  1. Start with the literal reading of the requirement: every view does UPDATE videos SET view_count = view_count + 1.
  2. Test it against the stated scale: a single viral video getting a million views an hour is roughly 300 writes per second, to one row, sustained — the exact hot-key shape the rate limiter's counter deep dive already covers, just for a different resource.
  3. Notice this is strictly worse than that earlier problem: a rate limiter's counter only needs to be roughly right for a few seconds; a view count is a row every reader hits on every page load, so the hot row is contended by writes and reads simultaneously.
  4. Apply the same two fixes already established elsewhere on this page, together: aggregate before writing (don't write per-event, batch the deltas), and split a single hot row into shards so no one row absorbs the full write rate.

A literal per-view increment against one row is the same hot-key problem as the rate limiter's counter — except contended by simultaneous reads (every page load) as well as writes, which makes it worse, not equivalent.

  • Aggregate before writing: the Stream Processor holds an in-memory running count per video and only flushes the accumulated delta every few seconds — a million individual increments can become a handful of batched writes.
  • Shard the hot video's counter: instead of one row per video, a viral video's count is split across several counter shards, written to round-robin — the same key-splitting technique from the Caching Playbook's hot-key section, applied to a counter instead of a cache entry.
  • The read path never touches this directly: readers see Cache, refreshed on an interval — the write-heavy aggregation path and the read-heavy display path don't contend for the same resource at all.

This only works because the requirement explicitly allows it: the count doesn't need to be exact or instant. If it had to be exact-to-the-view in real time, none of this would be available, and the system would need a fundamentally different, much more expensive design.

Key deep dive — what counts as a real view
FROnly past a watch thresholdNFRRoughly right, not exact
Thought process
  1. Start from the naive definition: a view is a page load. Test it against how people actually use the site — a page can load and the user leaves in half a second, or refreshes twice by accident.
  2. Notice "page load" measures interest in loading a page, not interest in the video — the two aren't the same thing, and the count is supposed to represent the second one.
  3. Move the trigger further into actual behavior: fire the event only once real watch-time crosses a threshold, so a bounce or an accidental double-load can't inflate the count on its own.
  4. Recognize a threshold alone doesn't stop deliberate replay — someone re-watching the same video five times in a row shouldn't count as five views, so identity and a time window matter too, not just watch duration.

"A view" sounds self-evident until it has to be encoded as a precise rule — page load, video start, and some meaningful watch duration are three different, defensible definitions, and the choice has real consequences for how easy the count is to inflate.

  • Trigger on watch-time, not page load: the client fires the event only after playback crosses a minimum duration (a common real-world choice is around 30 seconds, or completion for shorter videos) — a bounce never generates an event at all.
  • Deduplicate by viewer and time window in the Stream Processor: the same viewer_id/session replaying the same video within a short window (say, the same day) collapses into at most one counted view, without needing a synchronous check against a database on every single event.

This definition question has to be settled before any of the scaling work above matters — a perfectly scalable system that counts the wrong thing just produces a wrong number very efficiently.

Key deep dive — resisting bots without blocking real viewers
FRResist trivial inflationNFRMeasurably resistant to bot inflation
Thought process
  1. Notice the watch-time threshold from the previous deep dive stops accidental inflation, not deliberate inflation — a script can trivially fake "watched 30 seconds" without ever decoding a frame of video.
  2. Recognize this needs the same posture as the ticketmaster bot-prevention deep dive: no single check reliably tells a script from a person, so no single fix will be airtight.
  3. Attack it from more than one angle: make individual fake events costly to generate at scale, and make suspicious aggregate patterns detectable after the fact even when individual events look fine.
  4. Keep the two concerns separate: catching a bot in real time protects the count as it's written; catching a bot pattern retrospectively lets the count be corrected even after some bad data got in.

A watch-time threshold stops accidental double-counting; it does nothing against a script that simply claims to have watched 30 seconds thousands of times. Bot resistance is a different, additional problem layered on top.

  • Rate limit view events per client/IP — the same rate-limiter pattern used elsewhere on this page, aimed at the view-recording endpoint specifically.
  • Look for signals a real player naturally produces that a naive script doesn't bother faking — realistic watch-time distributions, player-state events at plausible intervals, not just a single "watched=true" event immediately after play started.
  • Retrospective anomaly detection: a video whose view count spikes far outside its normal pattern, or whose views cluster suspiciously by IP range or timing, gets flagged for review — this can correct the count after the fact, something the real-time path alone can't do.

Same lesson as the ticketmaster deep dive it mirrors: none of these are individually airtight, and a determined attacker adapts to any single one — which is exactly why real systems layer several imperfect defenses instead of searching for one perfect check.

Design a Global Unique ID Generator

zero-coordination · Snowflake-style · sortable by time

"Design a service that generates unique 64-bit IDs, at a rate of hundreds of thousands per second, across many servers in multiple data centers, with no two servers ever producing the same ID." The URL shortener already solved a version of "generate a unique ID" — by pre-allocating number ranges from one coordinating counter. That trick doesn't survive here: a request every few microseconds across data centers hundreds of milliseconds apart makes "check out a range first" itself the bottleneck. The real constraint is zero coordination, not less coordination — and the answer is encoding uniqueness into the structure of the number itself.

1
Requirements
Functional
  • Generate a unique ID on request, with no perceptible latency — this sits on the critical path of every write in whatever system calls it.
  • IDs are usable as primary keys — comparable, indexable, and (ideally) roughly sortable by creation time.
  • Any server, in any data center, can generate IDs independently at any moment.
Non-functional
  • Two different generator instances must never produce the same ID, under any circumstances — including a server restarting or briefly losing network connectivity.
  • No coordination between generator instances on the critical path — not a lock, not a database round trip, not a check against any other server, per ID.
  • Sustain a very high generation rate (hundreds of thousands of IDs/sec, aggregate) with each individual instance operating entirely independently.
  • IDs fit in 64 bits — small enough to be a practical, indexable primary key at scale, unlike a UUID's 128 bits.

Worth asking: does the ID need to hide creation time (privacy, avoiding a predictable sequence competitors could infer volume from), or is embedding timestamp for sortability actually desired? We'll assume sortability is a feature, not a leak — this is the common case for a primary key, and obfuscation is a separate, addressable concern if it's actually required.

2
Core Entities
  • SnowflakeID (timestamp_ms, datacenter_id, machine_id, sequence) — not a stored row; a 64-bit number whose bits are these four fields, packed together.
  • GeneratorInstance (datacenter_id, machine_id) — a fixed, unique identity assigned to each running generator at startup — the one piece of configuration the whole scheme depends on.
3
API

generate_id() → int64 — an in-process function call, not a network API. This is the entire interface: a library embedded in every service that needs an ID, running locally, calling nothing else to produce a result.

4
Data Flow — deliberately doesn't exist

There is no data flow to trace — that absence is the entire design. Generating an ID touches no network, no database, no other server; it reads the local clock and an in-memory counter and returns. The interesting engineering is entirely in the bit layout below, not in any request path.

High-Level Design

Deep Dives

Three below: (a) the bit layout, and why each field is sized the way it is, (b) clock drift and the one failure mode that actually threatens uniqueness, and (c) assigning machine IDs without a coordinator.

Uniqueness is a property of the bit layout, not of coordination. Two instances generating at the exact same millisecond still produce different IDs, because their (datacenter, machine) bits are baked in at startup and can never collide — there is nothing to synchronize.
Generating one ID
  1. Read the current time in milliseconds; subtract a fixed "epoch" (a custom start date) so the timestamp fits in fewer bits than the raw Unix epoch would need.
  2. Compare it to the last timestamp this instance used. If the clock has moved forward, reset the local sequence counter to 0.
  3. If the clock hasn't moved forward (multiple IDs requested within the same millisecond), increment the local sequence counter.
  4. Pack timestamp, this instance's fixed datacenter_id and machine_id, and the sequence into one 64-bit integer using bit shifts, and return it — no call to anything outside this process.
Two instances, same millisecond
  1. Instance A (datacenter 1, machine 7) and Instance B (datacenter 2, machine 3) each receive a request in the same millisecond.
  2. Both compute the identical 41-bit timestamp value — this part of their IDs genuinely matches.
  3. Their datacenter_id and machine_id bits differ, because those values were fixed and made unique at startup, before either instance ever generated an ID.
  4. The resulting 64-bit numbers are different by construction — no comparison against each other ever happened, and none was needed.
Key deep dive — the bit layout, and why each field is sized the way it is
FRSortable by creation timeNFRFits in 64 bitsNFRZero coordination
Thought process
  1. Start from the actual constraint: uniqueness has to come from the number's structure alone, since no coordination is allowed. That means the number needs enough distinct "identity" baked into it that two honest instances literally cannot produce the same one.
  2. List what's known and fixed about any given generator before it ever runs: which data center it's in, which specific machine it is. That's already two axes of guaranteed distinctness, for free, decided once at startup.
  3. Notice fixed identity alone isn't enough — the same instance, asked twice, needs its own two calls to differ too. Something has to vary within one instance's own output.
  4. Use time for that: it naturally increases, needs no coordination to read, and comes with a valuable side effect — a timestamp-prefixed number sorts roughly by creation order for free. Add a small counter only to break ties within the same millisecond.

A Snowflake-style ID packs four fields into one 64-bit integer via bit shifts — each field's size is a deliberate trade against how long the scheme lasts and how many machines it supports, not an arbitrary split.

  • 41 bits, timestamp in milliseconds since a custom epoch: the raw Unix epoch (1970) would waste decades of range before this system existed. A custom epoch (the scheme's own launch date) gets roughly 69 years of millisecond-resolution timestamps out of 41 bits — Unix time would need the same 41 bits to reach only until 2039.
  • 5 + 5 bits, datacenter_id + machine_id: 32 possible data centers, 32 machines each — 1,024 total generator instances active at once. Sized to the actual expected fleet, not maximized; more bits here means fewer bits left for timestamp or sequence.
  • 12 bits, sequence: resets to 0 every millisecond, incremented for each additional ID requested within that same millisecond — 4,096 IDs per instance per millisecond, or roughly 4 million IDs/sec per instance before this field would overflow.

This is the opposite trade-off from the URL shortener's counter-based ID: that scheme achieves uniqueness through one shared source of truth (a coordinated counter, or pre-allocated ranges from one); this scheme achieves it by making every instance's identity mathematically distinct from every other's, so there's no shared anything to coordinate.

Key deep dive — clock drift and the one failure mode that actually threatens uniqueness
NFRNever produce a duplicate ID
Thought process
  1. Audit the design for its one unverified assumption: everything above relies on each instance's local clock only ever moving forward.
  2. Ask what actually violates that in the real world — not a hypothetical, a known operational event: NTP clock synchronization can occasionally step a system clock backward to correct drift.
  3. Trace the consequence directly: if the clock goes backward, this instance could generate a timestamp it's already used, with a sequence counter that's already been through those same values — a genuine, concrete risk of a duplicate ID from the same machine.
  4. Since the fix can't be "make clocks never move backward" (not this system's to control), make the generator itself detect the condition and refuse to produce a possibly-duplicate ID rather than silently risk one.

Every field above assumes local clocks only move forward. That assumption can be violated — NTP synchronization occasionally steps a clock backward to correct drift — and this is the one failure mode that can actually produce a duplicate.

  • Detect it explicitly: on every ID generation, compare the current time to the last timestamp this instance used. If the current time is earlier, the clock has gone backward.
  • Refuse rather than risk it: a well-implemented generator throws an error or blocks briefly rather than silently generating an ID with a timestamp it may have already used — a short, rare unavailability is a far smaller cost than a duplicate primary key reaching a database.
  • Bound the blast radius: because datacenter_id and machine_id are fixed per instance, a clock issue on one machine can only ever risk colliding with that same machine's own past output — it can never collide with any other instance, anywhere.

This is the honest caveat worth stating plainly in an interview: "zero coordination" describes the common path, not an unconditional guarantee — the design still needs an explicit response to the one scenario where its core assumption can be violated.

Key deep dive — assigning machine IDs without a coordinator
FRAny server, any data center, independentlyNFRNo coordination on the critical path
Thought process
  1. Notice a gap in the design so far: it assumes every instance already has a unique machine_id, but never says how an instance gets one — and getting that wrong would break every uniqueness guarantee built on top of it.
  2. Consider a coordinator that hands out machine IDs on request. Test it against the whole point of this system — that's exactly the coordination being avoided, just moved to startup instead of per-request.
  3. Realize the constraint is actually softer than "no coordination ever" — it's specifically "no coordination on the hot path." A coordination step that happens once, at startup, is a completely different cost than one happening on every single ID.
  4. Choose a mechanism for that one-time step: something that already exists in most deployments and guarantees uniqueness on its own — a service registry, or simply a fixed value baked into configuration per deployment.

The whole scheme depends on every instance having a genuinely unique (datacenter_id, machine_id) pair — getting that wrong is the one mistake that defeats everything else, so it deserves as much attention as the bit layout itself.

  • This coordination happens once, at startup — not per-request, which is the actual constraint: "no coordination" describes generating an ID, not configuring the generator. A single lookup when a process boots is a fundamentally different cost than a lookup on every ID.
  • Common real-world approaches: register with a coordination service (ZooKeeper, etcd) on startup to claim an unused machine_id and hold it via a lease; or, simpler, bake a fixed machine_id into each server's deployment configuration if the fleet is stable enough to manage that by hand.
  • The failure mode to design for: if two instances are ever misconfigured with the same machine_id (a deployment mistake, not a runtime one), every uniqueness guarantee in this system silently breaks — worth a startup-time sanity check (claim-and-verify against a registry) rather than trusting static configuration alone at real scale.

"Zero coordination" is true of the hot path and false of bootstrapping — being precise about which one a claim applies to is exactly the kind of distinction worth making explicit rather than leaving implied.

Design a Stock Price Alert System

crossing detection, not point match · hot vs. illiquid tickers

"Any of 10–20M users can set a price alert on any of thousands of tickers — user A wants to know when BBCA crosses 3,000, user B wants to know when it crosses 3,100. When the price moves, every relevant alert has to fire, fast, exactly once, correctly." It reads like a fan-out problem, and partly is — but the sharper issue hides one level down: a price doesn't visit every value on its way up, and "does the new price equal this threshold" is the wrong question to be asking at all.

1
Requirements
Functional
  • Set an alert: ticker + threshold + operator (>, <, =, >=, <=).
  • An alert fires exactly once when the price satisfies its operator against the threshold, then deactivates.
  • A fired alert delivers a simple in-app push notification to the user's registered device.
  • A user can view and cancel their own active alerts.
Non-functional
  • Sub-second latency from a price tick to a crossing being identified — conditioned on a tick actually occurring, not a promise about tickers that aren't trading.
  • Scales to 10–20M users and thousands of tickers, each ticker receiving wildly uneven update frequency.
  • No missed crossings — a price that gaps straight across a threshold without ever equaling it still has to fire.
  • Listing or canceling a user's own alerts is a fast indexed lookup, never a scan across all alerts.
  • An offline user doesn't silently lose a fired alert forever, but staleness has a defined limit.

Worth asking: does = mean the price must land on that exact tick (rare, could go long stretches never firing on a fast-moving stock), or "reached this level from either direction"? We'll assume the latter — it turns out to be the same range-query mechanism as every other operator, just with the range collapsed to a single point, not a separate code path.

2
Core Entities
  • Alert (id, user_id, ticker, threshold, operator, status) — operator is one of >, <, =, >=, <=; status is Active or Triggered. Every write to this entity has to maintain two separate indexes, not one.
  • PriceTick (ticker, price, timestamp) — arrives on the Ingestion stream, partitioned by ticker symbol; not stored long-term, just the trigger for a range query.
  • TickerActivityState (ticker, tier, last_tick_at) — tier is Hot or Cold, decided by recent trading activity, not a fixed property of the ticker.
  • DeviceToken (user_id, push_token, platform) — the registered push token for the user's device, obtained once at app install/login; this is what delivery actually calls, not a live connection this system tracks itself.
3
API

POST /alerts {ticker, threshold, operator} → alert id
GET /alerts → the caller's own active alerts — served from the user_id index, never a scan
DELETE /alerts/{id} → cancels an active alert
Price ticks arrive on an internal stream, not through this API — this service consumes them, it doesn't expose a way to post one.

4
Data Flow — genuinely earns its place here
  1. A price tick for a ticker is published to the Ingestion stream, keyed by ticker symbol — every tick for that ticker always lands on the same partition, in order.
  2. The Detector instance assigned to that partition consumes the tick and looks up that ticker's sorted threshold index, asking for every threshold satisfying the relevant operators between the old price and the new price.
  3. Each matching Alert is marked Triggered — removed from the detection index so it can never fire twice.
  4. A trigger event is published to a separate queue — detection never waits on what happens next.
  5. A Delivery Worker consumes the event, looks up the user's push token, and calls the push provider — independently of how fast or slow that specific delivery turns out to be.
5
High-Level Design

Detection and delivery are two different systems connected by a queue, ingestion is partitioned before detection ever sees a tick, and every alert lives in two different indexes at once — diagrammed below.

6
Deep Dives

Five below: (a) crossing detection as a range query, not a point match, (b) partitioning the market feed so one Detector doesn't see every tick, (c) decoupling detection from push delivery, (d) hot tickers and illiquid tickers need opposite treatments, and (e) whether the User Alert Index actually holds up at 10–20M users.

An alert starts life at creation (0a/0b): the same write lands in both indexes at once, before any price ever moves. Ingestion then partitions the live market feed by ticker symbol before the Detector ever sees it — every tick for one ticker always lands on the same partition, in order, so a Detector instance can keep that ticker's Threshold Index warm without contending with every other ticker in the market. Two indexes, one write, two purposes: the Threshold Index answers "which alerts does this price move affect" (detection); the User Alert Index answers "what alerts does this user have" (listing).
A price crosses a threshold
  1. BBCA ticks 3,095 → 3,120. The Detector queries the Threshold Index for every alert between the two — a range, not a single value.
  2. User B's alert at 3,100 (crosses above) matches, even though 3,100 was never the exact tick.
  3. That alert is marked Triggered and removed from the index — it can't match twice, and stops taking up space in a structure about to be queried again.
  4. A trigger event publishes to the Trigger Queue. The Detector moves on immediately, not waiting on anything downstream.
A user checks their alerts
  1. The user opens the app; the client calls GET /alerts.
  2. Served entirely from the User Alert Index, keyed by user_id — a fast, indexed lookup, unrelated to detection's Threshold Index.
  3. Canceling an alert removes it from both indexes at once — it has to stop being detectable, not just stop being listed.
Key deep dive — crossing detection as a range query, not a point match
NFRNo missed crossingsNFRSub-second detection
Thought process
  1. Start with the check that sounds obviously correct: on every price tick, compare it to every alert's threshold — if new_price == threshold, fire.
  2. Test it against a real price move: 2,990 to 3,120 in one tick, on a fast-moving or illiquid stock. An alert at 3,100 is never equal to either endpoint — the naive check silently never fires, and nothing about the system flags that as wrong.
  3. Reframe the actual question: it was never "does the price equal this threshold," it was always "did the price pass through this threshold between the last tick and this one" — a range, not a point.
  4. Once it's a range question, the fix is a data-structure choice, not a smarter comparison: keep each ticker's active thresholds in a structure that answers "what's between X and Y" cheaply — a sorted set, not a list to loop over.

A per-alert equality check isn't just slow at scale — it's wrong at any scale, because a price move is a range, not a single value, and an alert sitting inside that range still has to fire even if the tick never lands on it exactly.

Range query: "thresholds in (2,990, 3,120], operator >" → A@3,000 matches, B@3,100 matches, D@3,150 does not (outside the range) → both A and B fire correctly, in one query against a sorted structure
  • What the index actually is: not a database index in the SQL sense — a sorted, in-memory structure, one per ticker, where the key is the threshold price. Concretely, a Redis sorted set: ZADD bbca_alerts 3100 alert_B. Internally it's a skip list, which is exactly what makes "give me everything between two values" a fast operation instead of a scan.
  • The range query itself: ZRANGEBYSCORE bbca_alerts 2990 3120 returns every alert with a threshold in that band directly — no loop over alerts that don't match.
  • All five operators are the same query, with the range boundaries adjusted: > and < use an exclusive boundary at the threshold itself; >= and <= use an inclusive one — a one-character difference in the query, not a different mechanism. = is the same query with the range collapsed to a single point (low == high == threshold), the smallest possible case of the identical detector.
  • Cancellation races against detection, the same shape as Ticketmaster's seat hold: a user can call DELETE /alerts/{id} at the exact instant a price tick is querying that same threshold. If cancellation just deletes the row, a tick that already read it before the delete could still fire it — the classic check-then-act gap. The fix is the same atomic remove used for firing: ZREM on the Threshold Index is itself atomic, so whichever happens first — the cancel or the detection's own removal-on-fire — wins outright, and the other finds nothing left to act on.
Illustration — the boundary is the only thing that changes between operatorsPrice ticks exactly onto 3,100 (from below, previous tick was 3,099): alert(threshold=3100, op=">") → range (3099, 3100] exclusive at 3100 → does NOT fire yet alert(threshold=3100, op=">=") → range (3099, 3100] inclusive at 3100 → FIRES alert(threshold=3100, op="=") → range [3100, 3100] single point → FIRES

Same instinct as the meeting room's overlap detection and the invoice search's anti-join — the fix in both cases was recognizing the real question is "what falls within this range," not "check this one thing against every candidate," and reaching for a structure built to answer range questions instead of a loop.

Is ZADD/ZRANGEBYSCORE actually the strongest choice?

It's the obvious default, not automatically the best one under real load. Two different bottlenecks — correctness and latency — call for two different fixes, worth separating rather than reaching for one upgrade that only solves one of them.

These four are not stages in a pipeline — they're four separate answers to one question: where does a hot ticker's Threshold Index actually live, and how do we touch it safely? Pick exactly one per ticker.

1. ZRANGEBYSCORE + separate ZREM

What's currently on this page. Query and removal are two round trips — fine at low tick rates, but the gap between them is a real correctness risk once tick frequency is high enough for another operation to land in between.

2. Lua script (EVAL) — same structure, used atomically

Bundles the range query, every removal, and the returned matches into one script Redis runs as a single indivisible step. Closes option 1's gap completely, on the exact same sorted set — no new infrastructure.

3. In-process tree, held in the Detector itself

Removes the Redis network round trip entirely — a real, fixed tax (commonly 0.1–1ms) paid on every tick. Raises a real question on crash: how does it come back correct? Detailed below.

4. Price-band sharding within one ticker

Orthogonal to the others — splits one ticker's own alerts by price range, not by ticker. Sounds simple; one wrinkle makes it less so. Detailed below.

Illustration — closing the atomicity gap with a Lua scriptWithout a script (two round trips): 1. ZRANGEBYSCORE bbca_alerts 2990 3120 → returns [alert_B] 2. ZREM bbca_alerts alert_B → a separate call ...another operation can land between steps 1 and 2 With EVAL (one atomic round trip): EVAL "local matches = redis.call('ZRANGEBYSCORE', KEYS[1], ARGV[1], ARGV[2]) for i,id in ipairs(matches) do redis.call('ZREM', KEYS[1], id) end return matches" 1 bbca_alerts 2990 3120 → query and every removal happen as one indivisible step; nothing can interleave
Illustration — option 3: what "in-process tree" means, and what happens when it crashesStructure: an in-memory balanced tree (e.g. a sorted map or skip list) per hot ticker, living inside the Detector instance's own process — no network call to query it. On a tick: tree.rangeQuery(old_price, new_price) → matches, purely in local memory. The real question this raises: the tree has no persistence. If this instance crashes, it's gone. What comes back on restart isn't automatic — it's a sequence: 1. Load every Active alert for this ticker from the durable User Alert Index — the actual source of truth, since the tree itself never was. 2. Rebuild the tree from that list. 3. Only then resume consuming ticks from this ticker's Kafka partition. Consuming ticks before step 2 finishes means querying an incomplete tree — a real crossing could be missed. The safe choice is a brief pause in detection for that one ticker during rebuild, not silently detecting against partial data.
Illustration — option 4: why one tick can span more than one price-band shardShards for BBCA, split by price band: bbca_alerts:0 → thresholds 0–3,000 bbca_alerts:1 → thresholds 3,000–6,000 bbca_alerts:2 → thresholds 6,000–9,000 ... Tick: price moves 2,990 → 3,120 — crosses the boundary between band 0 and band 1. Unlike ticker-sharding (a BBCA tick only ever touches BBCA's own shards), this single tick's range spans TWO price-band shards — the query has to check both and merge results, not query one shard and be done. A tick landing near a boundary is routine, not an edge case, so this multi-shard query is the common path, not a rare one. The bands aren't static either: if alerts cluster heavily around one round number, that band's own shard can go hot again — the same problem, one level down, needing its own re-split.
The actual fork: option 2 vs. option 3
Option 2 — Lua script on Redis

The alert data lives in Redis, reached over the network — but the query and every removal run as one atomic script.

  • Survives a Detector crash outright — the data lives in Redis, not in the process that died.
  • Every tick pays a small network round trip (~0.1–1ms) to reach Redis.
  • The safe default for essentially every ticker, hot or not.
Option 3 — in-process tree

The alert data lives inside the Detector's own memory — no network call, but nothing survives if that process dies.

  • A tick becomes a local function call — no network round trip at all.
  • A crash means the tree is gone — requires the load → rebuild → resume sequence above before it's safe to consume ticks again.
  • Only worth it once a ticker is provably hot enough that the network round trip itself matters.

Recommendation: option 2 as the default for every ticker, hot or cold — it fixes a genuine correctness gap in option 1 for free, using infrastructure already in place, so there's no real reason to skip it. Option 3 earns its added complexity only for tickers provably hot enough that the network round trip itself eats into the sub-second budget — and only alongside the crash-safe rebuild sequence above, since a stateful in-memory structure with no persistence isn't a free upgrade, it's a new failure mode to design for. Option 4 is worth knowing about, not worth building until a real ticker's alert count actually forces the question — the multi-shard query it introduces is real added complexity for what starts out solving a problem most tickers never have.

Key deep dive — partitioning the market feed so one Detector doesn't see every tick
NFRSub-second detectionNFRNo missed crossingsNFRScales to thousands of tickers
Thought process
  1. Notice everything in the deep dive above assumed a tick simply "arrives" at the Detector — worth checking what actually delivers it, especially with hundreds of liquid tickers all ticking through market hours at once.
  2. Consider one Detector process handling every tick for every ticker. Test it against real volume: that single process now has to keep every ticker's Threshold Index warm and reachable, and process a genuinely continuous, high-throughput stream alone — the exact bottleneck this whole design exists to avoid, just moved one step earlier.
  3. Consider the opposite: spread ticks across many Detector instances arbitrarily (round-robin). Test it against correctness: BBCA's own ticks could now land on different instances out of order, and the range query (old_price → new_price) depends on knowing the true previous price — an instance that missed the last tick has no reliable "old_price" to query from.
  4. Fix both problems with one choice: partition the stream by ticker symbol. Every tick for a given ticker always routes to the same partition, in the order it happened — that gives correctness (true order) and locality (one instance can keep that ticker's index warm) for free.

A price tick doesn't just "arrive" — with hundreds of liquid tickers ticking through market hours simultaneously, something has to decide which Detector instance handles which tick, and get the ordering right while doing it.

Illustration — partition by ticker, not round-robinKafka topic "price-ticks", key = ticker symbol Round-robin (wrong): BBCA's ticks scatter across partitions 0, 3, 1, 2, 0, 3... → no single Detector instance sees BBCA's ticks in order → "old_price" for the next tick is unreliable, range query can be wrong Partition-by-ticker (correct): key="BBCA" always hashes to the same partition, say partition 2 → every BBCA tick lands on partition 2, in the exact order the exchange emitted it → the Detector instance consuming partition 2 always has the true old_price → and can keep BBCA's Threshold Index shards warm, since it's the only instance touching them Is one consumer actually enough for BBCA's own volume? Check the numbers, don't assume: even an extremely liquid stock ticking every 50–100ms ≈ 10–20 ticks/sec one Kafka partition/consumer sustains tens of thousands of small messages/sec → BBCA's raw tick rate is 3–4 orders of magnitude below that ceiling — nowhere close to a bottleneck
  • Order is a correctness requirement here, not a nicety: Kafka guarantees order only within a partition, which is exactly why the key has to be the ticker symbol — anything else risks the Detector computing a crossing against the wrong "old_price."
  • A hot ticker needs isolation, not necessarily more consumers: hashing alone can still place BBCA on a partition shared with several moderately active tickers — a genuine problem, since one consumer now serves the combined tick rate of all of them. Pinning BBCA to its own partition fixes that, and one consumer is enough to keep up with a single ticker's actual volume; ingestion throughput was never the scarce resource here.
  • Don't confuse this with the Threshold Index's sharding — that bottleneck is real, this one usually isn't: a tick arriving is a tiny message; the range query it triggers against hundreds of thousands of alerts is genuinely expensive CPU/memory work. That's why the Threshold Index gets sharded across multiple Redis keys — the query workload, not the raw ingestion rate, is where a hot ticker's cost actually lives.

This is what actually makes the main diagram's single "Ingestion → Detector" arrow honest — not every tick funneling through one process, and not one dedicated instance per hot ticker either. It's a shared pool of Detector instances, each consuming one or more partitions, with known-hot tickers isolated onto their own partition specifically so their ticks never queue up behind a noisy neighbor's.

How "only one instance reads BBCA" is actually guaranteed

Not something the Detector's own code has to enforce — it's a built-in Kafka guarantee, in two parts: routing (which partition a tick lands on) and exclusivity (who's allowed to read that partition).

Illustration — BBCA, BBRI, BMRI, BBNI, routed and assignedPart 1 — routing (which partition does each ticker's ticks land on): key="BBCA" → pinned → partition 2 (dedicated — BBCA is known-hot) key="BBRI" → hash("BBRI") % 32 → partition 9 key="BMRI" → hash("BMRI") % 32 → partition 17 key="BBNI" → hash("BBNI") % 32 → partition 9 (shares a partition with BBRI — fine, neither is hot enough to need isolation) Part 2 — exclusivity (consumer group "detectors" — Kafka's own broker-side guarantee): partition 2 → Detector instance A, exclusively (BBCA's ticks — nothing else) partition 9 → Detector instance B, exclusively (BBRI + BBNI's ticks, in arrival order) partition 17 → Detector instance C, exclusively (BMRI's ticks) Kafka's group coordinator enforces this — two instances can never both be assigned partition 2 at the same time. Instance A never even sees a BBRI or BMRI tick; they were never routed to its partition in the first place.
  • Instance A doesn't filter out other tickers — it never receives them: exclusivity isn't a check inside the Detector's code ("is this BBCA? ignore it if not") — it's that BBRI, BMRI, and BBNI's ticks are routed to different partitions entirely, before any Detector ever sees them.
  • If instance A crashes, Kafka rebalances automatically: a missed heartbeat triggers reassignment of partition 2 to a different living instance — which starts with an empty local state and has to run the load → rebuild → resume sequence from the range-query deep dive above before it's safe to consume partition 2 again.
Key deep dive — decoupling detection from push delivery
FRPush notification on triggerNFRSub-second detectionNFROffline delivery, bounded staleness
Thought process
  1. Consider the simplest possible pairing: the moment an alert crosses, look up the user's device and send the push right there, in the same step as detection.
  2. Trace what a slow or unreachable push provider does to that: the Detector is now waiting on a network call to a third party before it can move on to the next tick — the exact bottleneck this system exists to avoid.
  3. Separate the two concerns explicitly: detection's job is "identify the crossing, fast" — delivery's job is "get the notification to the device, however long that takes" — and neither should block on the other.
  4. Once they're separate, decide the harder question: does marking the alert Triggered happen before or after delivery is confirmed? If before, a failed push means the alert is gone and the user never finds out. If after, a crash mid-delivery could leave a dangling Triggered-but-undelivered alert. Pick a default and be explicit about the failure mode either way.

The same "don't let the slow path block the fast path" instinct as the URL shortener's click analytics and Ticketmaster's confirmation email — except here the slow path is the entire point of the feature, which makes getting the failure mode right matter more, not less.

  • What "simple in-app push" actually means, mechanically: each device registers a push token with Apple (APNs) or Google (FCM) once, at install or login — that token is stored in DeviceToken Store as (user_id → token, platform). Delivering a notification means one API call to APNs/FCM with that token and the message; the provider handles finding and waking the actual device. This system never holds a live connection to anyone — that's the provider's job, not ours.
  • Kafka's role here is decoupling, not sharding: the Detector publishes a small "alert X triggered" message to a Kafka topic and immediately moves to the next tick — it never calls the Delivery Worker directly. Kafka's own internal partitioning (splitting the topic so multiple Delivery Worker instances can each consume a slice in parallel) is what lets delivery scale its own throughput independently — a different mechanism from sharding the Threshold Index, solving a different problem (parallel consumers, not one hot key's write throughput).
  • Deactivate at trigger time, retry delivery independently: the Alert is marked Triggered the moment the crossing is detected — that's the correctness guarantee ("fires exactly once"). Delivery is retried against the Kafka topic on its own schedule, decoupled from whether the alert itself is still Active; a failed push doesn't get a second detection, only a second delivery attempt.
  • Bounded staleness needs an actual mechanism, not just a stated limit: unlike a chat app, there's no "open the conversation and see what you missed." Each trigger event carries its own timestamp; the Delivery Worker checks it before every retry and simply drops the attempt once it's older than the bound (minutes, not hours) — the same short-TTL instinct as a cache entry expiring, applied to a queued notification instead of a stored value. If APNs/FCM reports the device unreachable and the window has already passed, it doesn't retry at all.

"Fired" and "delivered" are tracked as two different facts about the same alert — worth stating explicitly, since conflating them is exactly how a system ends up either double-firing on retry or silently losing a notification on failure.

Key deep dive — hot tickers and illiquid tickers need opposite treatments
NFRScales to thousands of tickersNFRSub-second, when a tick occurs
Thought process
  1. Notice the design so far quietly assumed every ticker behaves the same: ticks constantly, has a meaningfully sized alert index, needs to be fast at all times.
  2. Check that against thousands of real tickers: a handful trade every few hundred milliseconds with huge alert counts; most trade rarely, some go days between trades, with a handful of alerts each.
  3. Realize treating them identically wastes resources in both directions — a popular ticker's single index becomes a bottleneck under real load; an illiquid ticker's always-warm, always-sharded index costs the same as a hot one for almost no benefit.
  4. Split the strategy by actual behavior, not by a fixed list: let recent activity — not a static classification — decide which tier a ticker is in right now, and let it move between tiers as its trading pattern changes.

Thousands of tickers don't share one load profile — a fixed strategy tuned for either extreme wastes resources on the other. The fix is treating "how active is this ticker right now" as the thing that decides the strategy, not the ticker's identity.

Hot ticker (BBCA, ticks sub-second)

The bottleneck is throughput on a single ticker's own index — sharding spreads that one ticker's load, the same key-splitting instinct as the Caching Playbook's hot-key section.

  • Threshold Index is split into multiple shards for this ticker specifically; a tick queries all shards for that ticker in parallel and merges the matches.
  • A popular round-number threshold (3,000 on a major stock) can hold thousands of alerts — one crossing fans out that many trigger events at once, the same shape as the News Feed's celebrity fan-out, just aimed at a price level instead of a follower graph.
  • Kept always in memory — the cost is justified by the tick rate.
Illiquid ticker (barely trades)

There's no throughput problem to solve — the risk is the opposite one: paying hot-path memory cost for thousands of tickers that rarely justify it.

  • Its alert index lives in a cheaper, colder tier by default — not sharded, not necessarily in memory.
  • The sub-second NFR simply doesn't apply while there's no tick to measure latency from — worth stating explicitly rather than treating a dormant ticker as a violation.
  • On the rare tick, the ticker is promoted to the hot tier, its index warmed, and demoted back after a period of inactivity — activity decides the tier, not a fixed list.

Neither tier is the "correct" default for every ticker — the actual design decision is the promotion/demotion rule itself, since getting that threshold wrong either wastes memory on dormant tickers or adds a cold-start delay right when an illiquid ticker finally starts moving.

Key deep dive — the User Alert Index at 10–20M users
FRView and cancel own alertsNFRFast indexed lookup, never a scanNFRScales to 10–20M users
Thought process
  1. Notice this scale axis has gone unaddressed so far: every other deep dive scales with ticker count or tick rate — this one scales with user count, a completely different number, and it deserves its own check, not a free pass because "keyed by user_id" sounds like enough on its own.
  2. Estimate the real size: 10–20M users, a few alerts each, lands around 40–60M rows. Ask whether a plain B-tree index on user_id still holds up at that count.
  3. It does, for a reason worth stating rather than assuming: a B-tree index's lookup cost grows logarithmically with row count, so going from 1M to 60M rows adds a small, bounded number of extra comparisons — nothing close to the linear cost of a scan.
  4. Identify the one thing that actually could go wrong at this scale, and it isn't the index — it's a single unsharded PostgreSQL table absorbing 10-20M users' worth of concurrent connections and writes. That's a standard, well-understood scaling problem (read replicas, then partitioning by user_id range), not a novel one this design has to solve from scratch.

"Keyed by user_id" is repeated a few times in this design without ever being defended — worth checking it actually holds at 10–20M users rather than trusting the phrase on its own.

  • The index itself is not the bottleneck: a B-tree lookup on user_id is O(log n) — at 40–60M rows that's roughly 26 comparisons versus roughly 20 at 1M rows, an immaterial difference. This NFR was never actually at risk from row count alone.
  • The real scaling lever is standard relational-database practice, not something specific to this design: read replicas absorb GET /alerts traffic (reads dominate writes here — most users check their alerts far more often than they set or cancel one), and the table can be partitioned by a hash of user_id if a single primary node's write throughput ever becomes the actual constraint.
  • Why this doesn't need the Threshold Index's sharding treatment: that index gets hammered by every price tick across every alert on a ticker — write-heavy, latency-critical, sub-second. This one is read-mostly, and "fast" here means "a normal indexed query," not "sub-second under continuous write pressure" — a materially easier bar.

Not every NFR needs a novel mechanism — sometimes the honest answer is "a well-indexed table already clears this bar," and saying so explicitly is more useful than silence that reads as an oversight.

Tools you might reach for — and what each one is actually doing

Ingestion — Kafka, partitioned by ticker symbol

A separate topic (e.g. price-ticks) from the Trigger stream below — same technology, deliberately different partitioning strategy, for a different reason.

  • Its actual job: take the raw, continuous market data firehose and split it so no single Detector instance has to process every tick for every ticker — while guaranteeing each ticker's own ticks stay in order.
  • Why partitioned by ticker specifically, not round-robin: Kafka guarantees order only within a partition. Keying by ticker symbol means BBCA's ticks always land on the same partition in the order they happened — which the Detector's range query depends on, since it needs a reliable "old_price" for every new tick.
  • A known-hot ticker gets a dedicated partition, assigned deliberately, not left to hashing: even with partition-by-ticker, a hash could still place BBCA on a partition shared with several other active tickers — pinning it explicitly is what actually isolates its load.

Threshold Index (hot tier) — Redis Sorted Sets

One ZSET per hot ticker (e.g. bbca_alerts), split into shards (bbca_alerts:0…bbca_alerts:7) once one ticker's alert count justifies it.

  • Its actual job: answer "which alert IDs have a score (threshold) between X and Y" in O(log n + k) — internally a skip list, which is precisely the structure that makes a range query cheap instead of a scan.
  • Accessed via a Lua script (EVAL), not separate ZRANGEBYSCORE/ZREM calls: the query and every resulting removal run as one atomic step on the server, closing the gap where another operation could otherwise land between "find the matches" and "remove them."
  • Why sharded, not one key: Redis executes one command at a time per key. A single popular ticker's ZSET becomes a serialization point under real tick volume — splitting it lets a tick fan out to N shards in parallel and merge results, the identical key-splitting instinct from the Caching Playbook's hot-key section, applied to a sorted set instead of a cache entry.
  • What it does NOT do: it isn't durable storage — a Redis restart without persistence configured loses it. The alert's true state (Active/Triggered) lives in a durable store; this structure exists purely to make detection fast, and can be rebuilt from that source of truth if lost.

Threshold Index (cold tier) — PostgreSQL

A B-tree index on (ticker, threshold) for illiquid tickers that don't justify memory-resident, sharded storage.

  • Its actual job: the same range query as the hot tier (WHERE ticker = ? AND threshold BETWEEN ? AND ?), answered by a standard B-tree index — slower than a Redis skip list, but the ticker isn't ticking often enough for that gap to matter.
  • Why not just use Redis for everything: keeping thousands of rarely-active tickers' alerts warm in memory, sharded, costs real infrastructure for close to zero benefit — this tier is the deliberately cheaper default, promoted to the hot tier only on actual trading activity.

Trigger stream — Kafka

A second, separate topic (e.g. alert-triggers) from the Ingestion stream above — that the Detector publishes to and the Delivery Worker consumes from.

  • Its actual job: decouple detection from delivery — the Detector's only interaction with Kafka here is a fire-and-forget publish, so a slow or unreachable push provider can never add latency to the next price tick's detection.
  • Partitioned for consumer parallelism, not ordering: unlike Ingestion above (which must preserve per-ticker order), this topic's partitioning just needs to let multiple Delivery Worker instances each consume a slice concurrently — a genuinely different requirement from Ingestion's, even though both get loosely called "sharding" in conversation.
  • Why a queue and not a direct call: the Detector calling the Delivery Worker synchronously would reintroduce exactly the coupling this design exists to avoid — a queue lets each side fail, retry, and scale independently.

Push delivery — APNs / FCM

Apple's and Google's own push notification services — this system calls them, it doesn't reimplement what they do.

  • Their actual job: given a device's registered push token and a message payload, find and wake that specific device, even if it's asleep or the app isn't running — infrastructure this system deliberately doesn't build itself.
  • What this system is responsible for instead: storing the (user_id → push_token) mapping in DeviceToken Store, calling the provider's API with the right token, and handling the provider's response (delivered, token invalid, device unreachable) to decide whether to retry.
  • Why no connection registry is needed here: unlike a system that holds its own live WebSocket connections, a push token isn't a live connection to track — it's a stable identifier the provider resolves on their end. That's the whole reason this design is simpler than a system built around persistent server-held connections.

User Alert Index — PostgreSQL

A standard table with a B-tree index on user_id — this is the durable source of truth for every Alert, not just a read-optimized copy.

  • Its actual job: serve GET /alerts as a fast, indexed lookup, and hold the authoritative status (Active/Triggered) for every alert — the Threshold Index is a performance optimization built on top of this, not a replacement for it.
  • At 10-20M users: the index itself stays cheap (logarithmic lookup cost), so the real scaling levers are ordinary — read replicas for GET /alerts traffic, and partitioning by a hash of user_id only if write throughput on the primary ever becomes the actual constraint.
